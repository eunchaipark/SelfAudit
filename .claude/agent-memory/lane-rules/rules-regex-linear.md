규칙 정규식은 "시작 자리마다 줄 끝까지 읽는" 모양이면 먹보 한정자를 써도 제곱이 된다. 시작 자리를 `str.find`로 찾고, 실패하면 결과가 같을 수밖에 없는 구간(같은 덩어리)을 통째로 건너뛴다. 후보에는 범위만 두고 원문(`content[s:e]`)은 받아들인 걸림에서만 만든다.

**Why:** T5(F-S01)가 검토에서 보안 '중간' 2건으로 반려됐다(2026-11-19). `eyJ-` 반복 80KB가 5초, BEGIN 반복 270KB가 44MB. 기존 "긴 식별자" 성능 테스트는 사람이 고른 입력이라 이 모양을 놓쳤다.

**How to apply:**
- 정규식마다 "그 정규식의 머리말을 구분자로 반복" 입력(예: `eyJ-`*2만, `BEGIN…`*1만)으로 시간과 tracemalloc 최대 메모리를 잰다. 테스트로 남긴다.
- 같은 뜻으로 다시 짠 탐색은 명세 정규식과 고정 씨앗 무작위 입력으로 비교하고, 걸린 개수 하한도 단언한다(안 그러면 아무것도 검사하지 않는다).
- `\b`는 `pattern.match(s, pos)`에서도 pos 앞 글자를 본다(확인함).
- 재검증에서 두 번째로 반려됐다: 정규식만이 아니라 **발견마다 도는 곳**(근거 조각이 걸림 목록을 매번 다시 만듦)도 제곱이었다. 원문이 다른 걸림 1만~2만 개 입력으로도 잰다.
- T18이 세 번째 꼴로 반려됐다: **걸림이 없는 항목**마다 만드는 것(`.map` 항목 20만 개의 BOM 뗀 글·접두를 리스트로 쌓음, 입력의 2.8배). 항목·글을 하나씩 내는 제너레이터로, 접두 같은 부산물은 걸림이 있을 때만 만든다. main의 같은 입력과 최대 메모리 비율을 비교해 잰다(`.map` 항목 2만 개, main 1.7배).
- 명세 정규식을 다시 짤 때 결과가 명세 `finditer`와 같아야 한다(코드규칙 3장): 실패 뒤 다시 찾는 자리, 걸린 뒤 다시 찾는 자리(닫는 따옴표 뒤), `(?i)`가 `[A-Za-z]`에도 걸려 K(켈빈)·ſ·İ·ı를 받는 것까지. 무작위 대조는 `키+구분자+값` 틀을 흔드는 생성기로 만든다(문자 무작위로는 걸림이 거의 없다).
- 근거 조각에 표시 문자(사설 영역)를 넣는 방식은 대상 글과 부딪힌다. 앞·걸린 곳·뒤를 따로 만든다.
- `secrets._accepted`는 규칙 표 순서로 규칙마다 흘려 보며, 후보 생성기가 시작 순서로 낸다는 전제다. 새 규칙 생성기도 시작 순서로 낼 것.
- 새 worktree에서는 `cd frontend; npm ci`를 먼저 해야 check.py 화면 검사가 돈다.
- 반려 사유 `ops/검증/T<id>.md`는 main에만 있을 수 있다: `git show main:ops/검증/T<id>.md`.
