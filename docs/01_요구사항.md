# SelfAudit 요구사항

버전 0.1 · 작성 2026-11-18 · 다시 씀 2026-11-21 (목적 바뀜, D-035~D-038) · 주인: 문서 · 상태: 재설계 1단계 — 사용자가 재설계 초안을 확인함("진행", 2026-11-21). 기능명세는 아직 다시 쓰지 않았다

> 같은 AI 에이전트(Claude Code)가 내 웹 앱 빌드 결과물을 점검할 때, 역설계 도구 REA를 쥐여 주면 보안 문제를 더 많이·더 정확히 찾는지를 숫자로 보이고, 그 실험 도구를 만드는 과정에서 내 병렬 작업 방식이 한 세션보다 효율적인지를 같이 잰다.
> 이 문서의 모든 기준·값에는 '근거'가 붙는다(D-038). 근거가 추정이면 '추정'이라 쓰고 확인 방법을 적는다.
> 옛 목적(보안 자가진단 앱)의 요구사항 FR-01~FR-11·NFR-01~NFR-08은 10절에 그대로 남겼다.

## 1. 질문 (D-035)

| 질문 | 내용 | 사용자 말 (2026-11-21) |
|---|---|---|
| 질문 1 | REA(역설계 에이전트)를 쥐여 주면 Claude Code의 웹 빌드 결과물 보안 점검 성능이 높아지는가 | "1. 레아의 활용법 즉 역설계에이전트를 통해서 보안의 성능을 높일수 있는가" |
| 질문 2 | 이 프로젝트를 만드는 데 쓴 병렬 작업 방법(총괄 + 레인·검토 에이전트)은 한 세션보다 효율적인가 | "2. 프로젝트를 진행하면서 프로젝트 내가 만든 병렬활용법의 효율은 어떤가" |

- 성능은 재현율·정밀도·시간·비용으로 잰다(5.1). 효율은 시간·사용량·반려·잡은 결함·남은 결함으로 잰다(5.2).
- 근거: 질문 두 개는 사용자가 이 프로젝트로 얻고 싶다고 한 것 그대로다. '성능'과 '효율'을 숫자 몇 개로 나눈 것은 재설계 초안이고, 한 숫자만 보면 놓치는 쪽이 생겨서다(많이 찾아도 틀린 것이 많으면 쓸모가 없고, 빨라도 결함이 남으면 효율이 아니다).

보는 사람이 README 첫 화면과 보고서 두 개(R1·R2)만 읽고 아래 다섯 가지를 알 수 있어야 한다.

| # | 보여 줄 것 | 내용 |
|---|---|---|
| 1 | 질문 | REA가 AI 보안 점검을 낫게 하는가 / 병렬 방식이 낫는가 |
| 2 | 방법 | 무엇을 같게 하고 무엇만 바꿨는지(모델·지시문·대상·시간 상한은 같고 REA만 다름), 정답지는 어떻게 만들었는지 |
| 3 | 결과 숫자 | 조건별 재현율·정밀도·시간·비용, 난이도별 차이, 반복 N번의 범위(최소~최대) |
| 4 | 사례 | REA가 있어야만 찾은 것 2~3개, REA가 헛짚은 것 1~2개 — 실제 결과 조각과 함께 |
| 5 | 결론과 한계 | 한 문단 결론(꼴 예시, 가상 숫자: "REA를 쥔 Claude Code는 어려움 단계 비밀값 재현율이 33% → 83%, 정밀도는 비슷, 비용은 2.1배"), 이 실험이 말하지 못하는 것(대상 수, 웹 번들만, 모델 하나) |

- 근거: 질문·방법·결과·사례·한계는 실험 보고의 최소 구성이다. 하나라도 빠지면 보는 사람이 결과를 믿을 근거가 없다 — 방법이 없으면 공정했는지, 사례가 없으면 숫자가 무엇을 센 것인지, 한계가 없으면 어디까지 말할 수 있는지 모른다.
- 보고서를 둘로 나눈 근거: 질문이 둘이고, 재는 대상(점검 결과 / 만드는 과정)이 달라서다.
- 사례 수(2~3개, 1~2개)의 근거: 숫자가 무엇을 센 것인지 보이는 데는 몇 개면 되고, 많으면 보고서가 길어져 보는 사람이 끝까지 읽지 않는다(추정). 사례가 그만큼 나오지 않으면 나온 만큼 싣고 그렇다고 적는다.

## 3. 성공과 실패

| | 정의 | 근거 |
|---|---|---|
| 성공 | 두 질문에 **공정하게 잰 숫자 + 그 숫자가 나온 이유(사례)**로 답한 것. "REA가 별 차이 없다", "오히려 나쁘다", "병렬이 손해다"도 성공이다 | 목적은 REA가 낫다고 **보이는 것**이 아니라 낫는지 **알아내는 것**이다(사용자 질문이 "높일 수 있는가"). 'REA가 이기면 성공'으로 정하면 시험 번들을 REA에 유리하게 만들 유혹이 생겨 결과를 믿을 수 없다. 그래서 성공은 결과의 방향이 아니라 **잰 방법의 공정함과 재현성**으로 정한다 |
| 실패 | ① 조건이 같지 않았다(모델·지시문·대상·상한·REA 버전 중 바꾸려던 것 말고 다른 것이 달랐다) ② 원자료에서 숫자를 다시 계산할 수 없다 ③ 차이의 이유를 사례로 설명하지 못한다 | ①은 차이를 REA(또는 병렬 방식) 하나로 돌릴 수 없게 만든다. ②는 보는 사람이 숫자를 확인할 수 없게 만든다. ③은 숫자가 우연인지 실제 차이인지 가를 수 없게 만든다. 셋은 성공 정의의 '공정함·재현성·이유'를 하나씩 뒤집은 것이다 |

## 4. 결과물 (저장소에 남는 것)

| # | 결과물 | 무엇 | 다 됐다의 기준 | 그 기준의 근거 |
|---|---|---|---|---|
| R1 | **실험 보고서** `docs/보고서/REA실험.md` (+ 그림 2~3장) | 2절의 1~5 전부 (질문 1) | 표·그림·사례·결론·한계가 있고, 보고서의 숫자가 원자료에서 R5로 다시 계산한 숫자와 같다 | 다섯 요소는 2절의 근거. '다시 계산한 숫자와 같다'는 손으로 옮기다 생기는 오류를 막고, 보는 사람이 직접 확인할 수 있게 한다 |
| R2 | **병렬 효율 보고서** `docs/보고서/병렬효율.md` | 작업 쌍 비교 표(시간·사용량·반려·검토가 잡은 결함·병합 뒤 남은 결함), 사례, 언제 이득·손해인지 (질문 2) | 작업 쌍 3쌍 이상, '남은 결함'은 두 쪽 모두 같은 독립 검토로 잰다 | 1쌍이면 작업 난이도 차이와 방식 차이를 가를 수 없다. 3쌍이면 세 번 다 같은 방향인지 볼 수 있다(통계적 유의성은 아니며 한계에 적는다). 3쌍보다 많이는 주간 사용량으로 어렵다(지난주 한 창에 태스크 약 2개). 각 방식의 자체 검사는 기준이 달라서 같은 독립 검토라는 같은 자로 재야 비교가 된다 |
| R3 | **시험 번들과 정답지** `bench/bundles/`, `bench/answers/*.json` | 문제를 일부러 심은 웹 빌드 번들 6개 이상(쉬움·보통·어려움 2개씩), Juice Shop 공식 빌드와 알려진 문제 목록 | 정답지가 기계가 읽는 꼴이고, 정답마다 '어디에 무엇을 왜 심었나'가 있다 | 난이도를 나누는 것은 'REA는 숨기거나 난독화한 문제에서 차이를 낼 것'이라는 가설을 시험하려고. 난이도마다 1개면 번들 하나의 우연이 결과를 좌우해서 2개. 기계가 읽는 꼴이어야 채점이 사람 판단 없이 같게 나온다. '왜 심었나'는 헛짚음 판정의 근거가 된다. Juice Shop은 우리가 만들지 않은 바깥 정답지라 '내가 만든 번들이 REA에 유리하다'는 의심을 줄인다 |
| R4 | **실행기** `bench/run` | 조건 A·B로 대상마다 N번 Claude Code를 명령줄로 돌리고 결과·시간·토큰을 모은다. 실험 전용 설정 폴더 하나(A·B 같이)에 조건마다 다른 MCP 설정 파일을 `--strict-mcp-config`로 준다 | 명령 하나로 다시 돌릴 수 있고, 실행마다 원자료 `bench/results/<날짜>/…json`이 남는다 | 다시 돌릴 수 없으면 숫자를 확인할 수 없다(재현성). 설정 폴더가 하나이고 MCP 설정 파일만 다른 것은 `rea setup`을 쓰지 않아 클라이언트 전체 등록이 없고(D-040·D-041), 폴더를 둘로 나누면 로그인이 둘이 되어 어긋날 길이 생겨서다. A·B의 차이를 파일 하나로 줄이는 쪽이 '바꾸는 것은 REA 하나'(5.1)에 더 맞다 (design/bench-structure 브랜치 `docs/설계/실험구조.md`, 병합 전 6절 ②) |
| R5 | **채점기** `bench/score` | 결과 JSON ↔ 정답지 → 재현율·정밀도·위치 정확도, 표·그림 | 같은 원자료면 늘 같은 숫자가 나오고, 채점 규칙 시험이 있다 | AI 결과는 실행마다 흔들리는데 채점까지 흔들리면 어디서 생긴 차이인지 가를 수 없다 |
| R6 | **README** (저장소 첫 화면) | 1분 요약, 실험 구조 그림 한 장, 결과 요약 표, 다시 돌리는 법 | 처음 보는 사람이 5분 안에 다시 돌리는 법을 안다 | 포트폴리오를 보는 사람은 짧게 본다는 판단(추정). 5분은 정한 값이라 근거가 약하다 → 다 만든 뒤 처음 보는 에이전트에게 README만 주고 다시 돌리게 해 걸린 시간으로 확인한다 |

- 재현율 = 맞게 찾은 정답 수 ÷ 정답지의 정답 수. 정밀도 = 맞게 찾은 결과 수 ÷ 낸 결과 수. 예(가상 숫자): 정답 6개인 번들에서 결과 5개를 냈고 그중 4개가 정답과 맞으면 재현율 4 ÷ 6 = 66.7%, 정밀도 4 ÷ 5 = 80.0%. '맞음'으로 볼 위치 범위는 미결(8절 3).
- 근거: 재현율은 '더 많이 찾는가', 정밀도는 '더 정확히 찾는가'를 가른다. 둘 중 하나만 보면 결과를 많이 쏟아 내는 조건이 유리해진다.
- 다 된 차례: R3 → R5 → R4 → 첫 실험 → R1 초판 → 넓히기(Juice Shop, N 늘리기) → R1·R2·R6 완성(재설계 초안 6절). 근거: 정답지가 있어야 채점 규칙을 시험할 수 있고, 채점기가 있어야 실행기의 출력 꼴을 확인할 수 있다.

## 5. 실험의 틀

### 5.1 질문 1 — REA 실험 (D-036)

| 조건 | 무엇 |
|---|---|
| A | Claude Code — 파일 읽기·검색 도구만 (REA 없음) |
| B | Claude Code + REA (MCP 또는 CLI, 설계가 정한다) |
| C (선택) | 사람이 짠 규칙 검사기 — AI 없는 바닥값. 옛 비밀값·소스맵·내부 주소 점검 코드 |

| 항목 | 정한 것 | 근거 |
|---|---|---|
| 바꾸는 것 | A와 B는 REA 하나만 다르다 | 바꾸는 것이 둘이면 차이가 어느 쪽 때문인지 모른다 |
| 같게 하는 것 | 모델, 지시문, 시간·비용(토큰 환산) 상한, REA 버전(고정), 대상. 토큰은 실행마다 기록한다 | 위와 같다. REA 버전 고정은 REA 문서가 '빨리 바뀐다'고 해서, 실험 중 버전이 바뀌면 차이가 REA 버전 때문인지 알 수 없어서다. 상한을 토큰이 아니라 비용으로 두는 것은 Claude Code 명령줄에 토큰 상한 인자가 없고 `--max-budget-usd`만 있어서다. 같은 모델이면 금액 = 토큰 × 값이라 같은 일을 한다 (design/bench-structure 브랜치 `docs/설계/실험구조.md`, 병합 전 6절 ①) |
| 대상 | ① 시험 번들(R3) — 평문·나눠 쓴·난독화된 비밀값, 소스맵, 내부 주소·관리 경로, 숨은 API 라우트, 화면에만 있는 권한 검사, 디버그 플래그, 옛 버전 라이브러리. 쉬움·보통·어려움 ② OWASP Juice Shop 공식 배포본 — 실행하지 않고 빌드 결과물만 | ①은 정답을 우리가 알아 재현율을 셀 수 있다. ②는 R3 근거의 '바깥 정답지'. 실행하지 않는 것은 점검 대상이 빌드 결과물이고, 대상 앱을 돌리면 실험 밖의 위험(포트·네트워크)이 생겨서다 |
| 반복 | 같은 대상을 조건마다 N번, 처음 N = 3 | 3은 범위(최소~최대)를 보고 튀는 값 하나를 알아볼 수 있는 가장 작은 수다. 사용량이 N에 비례해서 3으로 시작하고, 흔들림이 크면 늘린다('크다'의 값은 미결, 8절 5) |
| 결과 형식 | 정해진 JSON(종류·파일·위치·근거·확신) → R5 | 꼴이 정해져야 채점이 사람 판단 없이 같게 나온다. 필드 이름은 미결(8절 3) |
| 첫 실험 | 번들 6개 × 조건 A·B × 3번 = 36번. 밤사이 자동 실행 (사용자 허락 2026-11-21) | 6 × 2 × 3 = 36. 36번이 하룻밤 사용량에 들어가는지는 모른다(추정) → 처음 2~3번을 돌려 1번 비용을 잰 뒤 나머지를 정한다. 빈 실행 2번(대상 없이 고정 비용 재기)·문지기 실행 2번(작업 폴더 밖 읽기가 막히는지 확인)은 '처음 2~3번'과 따로 센다 — 대상을 점검하는 실행이 아니라 그 비용을 가르는 데 쓰는 짧은 실행이라서다 (design/bench-structure 브랜치 `docs/설계/실험구조.md`, 병합 전 6절 ③) |
| 조건 C | 선택 | 'AI가 사람이 짠 규칙보다 나은가'라는 바닥값을 주지만 질문 1의 핵심(REA의 효과)이 아니다 |

### 5.2 질문 2 — 병렬 효율 비교군 (D-037)

| 항목 | 정한 것 | 근거 |
|---|---|---|
| 비교 단위 | R3~R5를 만드는 작업 가운데 비슷한 크기의 **다른** 작업 쌍. 하나는 병렬(레인 + 검토 + 총괄), 하나는 한 세션이 나누지 않고 만든다. 같은 명세, 같은 검사 | 같은 작업을 두 번 만들면 두 번째가 첫 번째를 보고 배워 공정하지 않다 |
| 크기 맞추기 | 명세 예시 수·바뀔 파일 수로 맞춘다 | 둘 다 만들기 전에 셀 수 있는 크기다. 완벽히 같을 수 없음은 R2 한계에 적는다 |
| 남은 결함 | 둘 다 병합 뒤 같은 독립 검토(보안·명세)를 한 번 더 돌려 센다 | 각 방식의 자체 검사는 기준이 달라 같은 자가 필요하다(R2 근거) |

## 10. 옛 목적 (2026-11-17~21, 대체됨)

> D-035(목적 바뀜)로 대체됐다. 지우지 않고 남긴 것은 기능명세·화면정의·태스크가 아직 이 번호(FR-·NFR-)를 가리키고, 번호가 문서에 남아 있어야 다시 쓰이지 않기 때문이다. 아래는 2026-11-21 전 내용 그대로다(절 번호만 10.x로).
> 내 앱의 빌드 결과물을 공격자 시점에서 스스로 점검하고, 고친 뒤 전후를 비교하는 보안 자가진단 도구.
> 첫 버전(MVP)은 **웹 번들**만 다룬다(D-008). 기능의 자세한 규칙과 예시는 `docs/02_기능명세.md`, 화면은 `docs/03_화면정의.md`.

### 10.1 목적과 사용자

| 항목 | 내용 |
|---|---|
| 사용자 | 웹 앱을 만들어 배포하려는 개발자 한 명 (이 PC의 주인) |
| 해결할 문제 | 빌드해서 내보낸 번들에 비밀값·원본 코드·내부 주소·낡은 라이브러리가 남았는지, 배포 전에 공격자처럼 확인하기 어렵다 |
| 성공 기준 | 연습용 앱 번들 하나를 넣으면 발견 목록과 점수가 나오고, 고친 뒤 다시 넣으면 '고쳐짐·남음·새로 생김'과 점수 변화가 보인다 |
| 포트폴리오에서 보여 줄 것 | 점검 결과 화면, 전후 비교 화면, 내보낸 리포트로 Claude Code에서 설명 받는 흐름 |

### 10.2 범위 원칙

- 분석 대상: 내가 만든 앱, 분석이 허용된 공개 연습용 앱만 (D-006).
- 실행: 내 PC 로컬(127.0.0.1)만. 배포하지 않는다 (D-007).
- LLM: 앱 안에 없다. 결과를 내보내고 Claude Code에서 설명을 받는다 (D-012).
- REA: 있으면 참고로만 쓰는 보조 엔진 (D-011). 설치는 사용자가 정한다 (D-024).
- 사용자가 직접 할 일: 취약 라이브러리 목록(RetireJS `jsrepository-v4.json`)을 브라우저로 받아 `<데이터 폴더>/vulndb/jsrepository.json`에 둔다. 없어도 다른 점검은 된다 (D-016).
