# CR-002 T5·T9 구현이 고른 세부를 명세로 확정 (F-S01 위치·자리표시값·근거 조각·겹침·`.map`, F-C01 줄바꿈)

상태: 반영됨
크기: 명확화
요청: T5 보고서 '명세와 달라진 점' (1)~(7) / 검증 T5 '재검증 2'·'재검증'의 '병합 뒤 CR 분석으로 넘길 것'·'고치지 않을 것' / T9 보고서 '명세와 달라진 점' / 검증 T9 '명세에 없음 1' (모두 main 6209b15)
원래 말: "명세 규칙 표·처리 규칙과 다르게 만든 것은 없다. 다만 명세가 정하지 않아 내가 고른 것이 있고, 결과가 명세 문장만으로는 정해지지 않는 것이 둘 있다((6)(7), 검증 '고치지 않을 것', 병합 뒤 CR 분석 대상)." (ops/보고/T5.md) / "병합 뒤 CR 분석으로 넘길 것: 보고서 '명세가 정하지 않아 고른 것' (1)~(7), 근거 조각 안 짧은 값 원문, `(?i)` 식별자 의도, 파일당 발견 수 상한." (ops/검증/T5.md) / "한 가지만 명세가 정하지 않았다: 이름에 줄바꿈이 들어 있으면 그대로 둔다." (ops/보고/T9.md)
목적: 구현이 명세 없이 고른 동작을 명세로 확정하거나 바꿀지 사용자가 정할 수 있게 한다 — 번들에서 비밀값 노출을 찾는다 (FR-03) · 같은 앱의 두 점검을 비교해 고쳐짐·남음·새로 생김과 점수 변화를 보여 준다 (FR-10)
기술 검토 필요: 아니오 (모든 항목의 추천안이 지금 구현 그대로다. 계약·폴더·공통 파일·마이그레이션·새 라이브러리 없음. 추천이 아닌 안을 고르면 그 항목만 레인 수정 태스크가 생긴다)

## 무엇을, 왜
T5(F-S01)와 T9(F-C01) 레인이 명세가 정하지 않은 가장자리 동작을 골라 구현했고, 검토가 이를 반려하지 않고 CR 분석으로 넘겼다. 이대로 두면 다음 레인(T6 F-S02·S03은 같은 근거 조각 도구를 쓴다)과 spec-checker가 다른 기준으로 볼 수 있다. 항목마다 선택지와 지금 구현을 적었다.
보안 쪽 보강(근거 조각 안 짧은 값, 파일당 걸림 상한, `.map` 이름 글, zip 이름의 제어 문자)은 동작이 바뀌고 설계 검토가 필요해 **CR-003**으로 나눴다.

## 항목별 선택지 (★ = 지금 구현, 추천은 각 항목 끝)

**(1) 발견 위치는 어디를 가리키나 (F-S01)**
- 안 A ★: 값(원문)의 첫 글자. S01-GENERIC도 키 이름이 아니라 값 위치. `password:"hunter2hunter2"` → 1:11
- 안 B: 정규식 전체 매치의 첫 글자(GENERIC은 키 이름). 같은 입력 → 1:1
- 추천 A: 명세 AWS 예시(3:15는 따옴표 다음 `A`)와 CR-001의 '겹침은 값 범위'와 같은 기준이다. 코드·테스트 그대로.

**(2) 자리표시값은 어떻게 맞추나 (F-S01 3)**
- 안 A ★: 명세에 `…`가 붙은 `your…`·`example…`·`process.env…`는 앞부분이 같으면, `changeme`·`placeholder`는 값 전체가 같을 때만, `<…>`·`${…}`는 그 글자로 시작하고 끝날 때, 한 글자 반복은 대소문자 무시로 값 전체. `changeme123`·`placeholder1` → 발견
- 안 B: `changeme`·`placeholder`도 앞부분 일치. `changeme123` → 버림
- 안 C: 다섯 낱말이 값 어디에 들어 있어도 버림
- 추천 A: 명세 글자(`…` 유무)를 그대로 읽은 것이고, `changeme123`은 실제로 쓰이는 약한 비밀번호라 놓치는 쪽보다 알리는 쪽이 낫다.

**(3) 근거 조각 ④⑤를 어떤 글에서 세나 (1절 '근거 조각', 모든 규칙)**
- 안 A ★: ④ 앞뒤 40자는 ②③(가리기)을 한 **뒤의 글**에서 센다. 그래서 가린 값 중간에서 잘릴 수 있다(`A****LE" ab…`). ⑤는 ④ 뒤에 하고 `\r\n`·`\r`·`\n` 하나를 공백 하나로 바꾼다
- 안 B: ④를 원문 위치로 세고 자른 뒤 가린다 — 비밀값이 중간에서 잘리면 남은 조각이 규칙에 안 걸려 원문 일부가 드러날 수 있다
- 추천 A: 명세의 ①~⑤ 순서 그대로이고, 원문 조각이 남을 길이 없다.

**(4) `.map`이 JSON 객체가 아닐 때 (F-S01 입력·9, F-S02 예외)**
- 안 A ★: JSON 오류뿐 아니라 배열·숫자 같은 객체가 아닌 JSON도 S01은 보지 않는다(발견 0). 객체인데 `sourcesContent`가 없으면 발견 0(날글로 다시 보지 않는다). F-S02 예외 '소스맵 형식 아님'도 'JSON 객체가 아님'으로 맞춘다
- 안 B: 객체가 아니면 날글로 S01을 돌린다
- 추천 A: F-S02 예외의 "이 파일은 F-S01·S03도 보지 않는다"와 같다. T6(F-S02, pending)이 시작하기 전에 정해 두면 두 규칙이 어긋나지 않는다.

**(5) `.map` 항목에 이름이 없거나 내용이 글이 아닐 때 (F-S01 9)**
- 안 A ★: `sourcesContent`의 null·빈 글·글이 아닌 항목(숫자 등)은 건너뛴다. 같은 번째 `sources` 이름이 없거나(목록이 짧음·없음) 글이 아니면 접두는 `[] `
- 안 B: 이름이 없으면 접두를 붙이지 않는다
- 안 C: 이름이 없으면 `[#<번째, 0부터>] `
- 추천 A: 내용 거르기는 F-S02 1(빈 문자열·null은 내용 없음)과 같고, `[] `는 '이름 모름'을 드러낸다. 드문 경우라 바꿀 이득이 작다. (이름 글 자체의 줄바꿈·길이는 CR-003 (c))

**(6) 근거 조각 ③이 걸린 곳에 닿을 때 (1절 '근거 조각')**
- 안 A ★: **이 발견**의 가린 값은 앞뒤 글과 잇지 않는다(앞·걸린 곳·뒤를 따로 ③). 다른 걸림의 가린 값은 `*`에서만 끊긴다. `abcdefghijklmnopqrstu-AKIAIOSFODNN7EXAMPLE` → `abcd****AKIA****LE`
- 안 B: 명세 글자대로 범위 전체에 한 번 ③. 같은 입력 → `abcd********LE`(어느 키인지 안 보이고 ④의 '걸린 곳'이 사라진다)
- 안 C: 범위 안 **모든** 걸림의 가린 값을 잇지 않는다. 아래 예시의 둘째 발견이 `abcd****AKIA****LE AKIA****LE`가 된다(코드 수정)
- 추천 A: ④가 기준으로 삼을 걸린 곳이 늘 남고 코드를 고치지 않는다. A와 C가 갈리는 것은 `\b` 앞 글자가 `-`·`+`·`/`·`=`이고 그 앞에 20자 이상 덩어리가 붙은 드문 경우뿐이다.

**(7) 같은 규칙 안에서 값 범위가 겹칠 때 (F-S01 2·4)**
- 안 A ★: 규칙 사이와 같이 먼저 시작한 것만 남긴다. 실제로 겹칠 수 있는 것은 S01-PKEY뿐(나머지 규칙은 걸림이 서로 겹치지 않게 나온다): END 없는 BEGIN의 4,096자 안에 다른 블록이 들 때, BEGIN 둘에 같은 종류 END 하나일 때 → 발견 1
- 안 B: 개인키 블록을 다음 BEGIN 앞에서 끊는다(END가 다음 BEGIN보다 뒤에 있으면 'END 없음'으로 보고 4,096자와 다음 BEGIN 앞 중 짧은 쪽까지). 위 두 경우 → 발견 2
- 추천 A: 처리 규칙 2를 같은 규칙에도 넓히는 한 줄로 끝나고 코드 그대로다. 단점: 바깥 조각을 지우고 다시 점검하면 안쪽 키가 '새로 생김'으로 보인다(F-C02). B는 더 정확하지만 개인키 후보 만들기(T5에서 메모리 반려를 두 번 고친 곳)를 다시 고쳐야 한다.

**(8) GENERIC 정규식 `(?i)`가 유니코드 글자도 받는가 (F-S01 규칙 표)**
- 안 A ★: 파이썬 `re`의 유니코드 대소문자 무시 그대로. `[A-Za-z]`와 키워드가 K(U+212A 켈빈)·ſ(U+017F)·İ(U+0130)·ı(U+0131)도 받는다. `paſſword:"abcdefgh12"`·`api_` + U+212A + `ey:"abcdefgh12"` → 발견. `passwordé:"abcdefgh12"` → 발견 없음
- 안 B: ASCII만(`re.ASCII`, `(?ai)`). 위 두 입력 → 발견 없음. 코드 한 곳과 대조 테스트의 기준 정규식이 바뀐다(기대값 변경)
- 추천 A: 명세 정규식을 쓰인 대로 돌린 결과이고 더 많이 찾는 쪽이다. 실제 번들에 이런 글자가 나올 일은 거의 없어 바꿀 이득이 작다. 명세에 한 줄만 적어 다른 사람이 다시 짤 때(JS `/i`는 이렇게 안 한다) 어긋나지 않게 한다.

**(9) 파일 이름에 줄바꿈이 있을 때 (F-C01 1)**
- 안 A ★: 정규식은 이름 **전체**에 맞아야 지운다(`re.fullmatch`와 같은 뜻, `.`은 줄바꿈을 건너지 않는다). 그래서 줄바꿈이 든 이름은 그대로. `index-BmR2x9Qa.js\n` → 그대로
- 안 B: 파이썬 `re.match`의 `$`처럼 끝 줄바꿈 하나 앞에서도 맞춘다. 같은 입력 → `index.js`
- 추천 A: B는 정규식 엔진의 버릇일 뿐 근거가 없다. 줄바꿈이 든 이름이 아예 들어오지 않게 하는 것은 CR-003 (d)(F-I01 zip 이름).
