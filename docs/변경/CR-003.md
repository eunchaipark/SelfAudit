## 무엇을, 왜
T5 검토가 반려하지 않고 넘긴 보안 건이다. 지금 구현은 명세대로지만, 명세대로면 (a) 내보내기 파일(F-E01·E02, 화면 알림 "비밀값은 가려져 있습니다", Markdown 머리 "이 파일에는 비밀값 원문이 없습니다")에 규칙에 걸리지 않은 짧은 비밀번호가 남을 수 있고 (b) 걸림이 빽빽한 큰 파일에서 메모리가 걸림 수에 비례해 는다. (c)(d)는 분석 대상에서 온 이름 글이 거르지 않고 결과에 들어가는 건이다.
CR-002(같은 F-S01의 명확화)를 먼저 반영하고 이 CR의 영향을 다시 찾는다(문서 카드 '한 번에 하나씩').

## 항목별 선택지 (★ = 지금 구현)

**(a) 근거 조각 범위 안의 걸리지 않은 짧은 값 (1절 '근거 조각' ②, 모든 규칙)**
- 안 A ★: 지금대로(S01 걸림과 20자 이상 덩어리만 가린다). 명세에 알려진 한계 한 줄을 적고, 화면 알림·Markdown 머리 문구를 "규칙에 걸린 비밀값은 가려져 있습니다"처럼 고친다
- 안 B: ②에서 S01 걸림에 더해, GENERIC 키워드(`password` 등)가 든 식별자 + `["']?\s*[:=]\s*` 뒤의 값을 길이·자리표시값과 상관없이 `****`로 가린다. 값: 따옴표로 열리면 같은 따옴표 앞까지(범위 안에서 닫히지 않으면 범위 끝까지), 따옴표가 없으면 공백·따옴표·`,;)}]` 앞까지. 근거 조각에서만 가리고 발견은 만들지 않는다
- 안 C: B에 더해 범위 안의 따옴표 글을 모두 `****`로 가린다(가린 값은 그대로)
- 추천 B: 흔한 꼴(`password:"abc12"`, `password = abc12345xyz`)을 막으면서 코드 맥락은 남긴다. C는 가장 안전하지만 근거 조각이 거의 뼈대만 남아 S03 등에서 쓸모가 줄어든다. B로도 `var pw='hunter2'`(`pw`는 키워드가 아님)는 남는다 — 그것까지 막으려면 C
- 설계 확인: B·C 정규식의 선형 시간(GENERIC처럼 키워드를 먼저 찾기), T6(S03)도 같은 `build_snippet`을 쓰므로 함께 적용

**(b) 파일 하나의 걸림 수 상한 (F-S01, 메모리)**
- 안 1 ★: 상한 없음. F-I01의 파일 50MB·합 200MB 상한에 맡기고 명세에 알려진 한계로 적는다. 잰 값(이 CR 작성 때, main 6209b15): 서로 다른 AWS 키 1만 개(210KB) 최대 메모리 7.3MB, 10만 개(2.1MB) 75.6MB — 입력의 약 35배라 빽빽한 50MB 파일은 약 1.7GB로 추정
- 안 2: 파일 하나(`.map`은 항목을 모두 합쳐)에서 받아들인 S01 걸림(묶기 전)이 **10,000개**가 되면 그 파일의 S01을 멈춘다. 그때까지 받은 발견은 남기고, 건너뜀 목록에 그 파일을 이유 `걸림이 너무 많아 일부만 점검`으로 남긴다. 메모리는 위 잰 값으로 약 7MB 안팎
- 안 3: 묶은 뒤 발견 1,000개 상한(넘는 발견은 버리고 같은 알림). DB·화면·내보내기 크기는 막지만 걸림 수에 따른 메모리는 그대로
- 추천 2: 검토가 지적한 원인(걸림 수에 비례)을 직접 막고 DB·화면 크기도 함께 묶인다. 단점: 멈춘 파일은 뒤쪽·뒤 규칙(GENERIC·GAPI 등) 결과가 빠지고, 같은 키가 1만 번 넘게 나오면 횟수가 10,000에서 멈춘다. 숫자(10,000)는 사용자가 정한다
- 설계 확인: 멈추는 단위(규칙마다/파일 전체), 건너뜀 이유를 규칙 함수가 어떻게 돌려주는지(지금 `scan_file`은 발견 목록만 돌려준다 → 계약), S03(T6)도 같은 상한을 둘지

**(c) `.map` `sources` 이름 글 (F-S01 9)**
- 안 A ★: 이름을 그대로 `[<이름>] `으로 붙인다. 줄바꿈·길이 그대로(`sources` `["a\nb.ts"]` → 근거 조각 `[a`↵`b.ts] password:"****"`)
- 안 B: 이름에도 ⑤(줄바꿈 → 공백)를 하고 100자를 넘으면 앞 100자 + `…`. 같은 입력 → `[a b.ts] password:"****"`
- 추천 B: 근거 조각 안에 줄바꿈이 남지 않는다는 ⑤의 뜻과 맞고, 이름 하나가 수 MB여도 조각이 커지지 않는다. 숫자(100)는 사용자가 정한다. Markdown은 F-E02 3이 칸을 200자로 다시 자른다

**(d) zip 항목 이름의 제어 문자 (F-I01 B 2ⓑ)**
- 안 A ★(명세 없음): 정하지 않는다. T4(pending) 구현에 따라 풀다가 OS 오류("점검 중 오류가 나서 멈췄습니다")가 되거나 이름이 그대로 F-C01까지 간다
- 안 B: 조각에 제어 문자(U+0000~U+001F)가 있으면 실패(Windows 이름). Windows는 이 글자를 파일 이름에 쓸 수 없으므로 폴더 입력(F-I01 4)에서는 나올 수 없다
- 추천 B: T4가 시작하기 전이라 비용이 작고, 줄바꿈이 든 경로가 F-C01(CR-002 (9))·화면·내보내기에 들어올 길이 막힌다
- 설계 확인: 보안규칙 5장 'zip 항목' 줄과 맞추기(설계의 파일), 실패 이유의 `<항목>`에 제어 문자가 든 이름을 어떻게 보일지

    - 안 A는 코드가 그대로지만 F-E02 머리 문구와 SCR-04 04-06 알림 문구가 바뀐다(T11·T12·T17).
  - **(b) 안 2 가능, 비용 중간, 상한 10,000은 파일 하나에는 맞다**
    - 메모리는 걸림 하나에 약 0.73KB다(원문이 다른 AWS 1만·2만·4만 개 → 최대 7.3·14.7·29.5MB). 상한 10,000이면 파일 하나는 '글 + 약 7MB'로 묶인다. 원문은 겹치지 않으므로 묶기 표의 원문 키 합도 글 길이를 넘지 않는다. 실제 번들에서 한 파일에 S01이 1만 개 걸리면 생성된 데이터나 테스트 묶음이라고 봐도 된다.
    - **빠진 것: 점검 전체 상한.** 파일 상한만으로는 점검 하나가 묶이지 않는다. 200KB짜리 파일 1,000개(합 200MB, F-I01 안)가 저마다 걸림 1만 개면 발견이 1,000만 개다. `RuleRun`이 이것을 한 번에 들고 있으면(발견 하나 약 0.45KB) 4.5GB이고, DB 행도 1,000만 개가 된다. 점검 전체 발견 수 상한을 함께 정하길 권한다. 제안은 **50,000개**(메모리 약 25MB, DB 약 20MB)다. 넘으면 남은 파일의 S01~S04를 멈추고 안내 한 줄(`notices`)을 남긴다. 숫자와 문구는 사용자가 정한다.
    - 멈추는 단위는 '파일 하나 · 규칙 묶음(F-S01 전체)'을 권한다. S01 규칙은 규칙 표 차례로 흘려 보며 판정하므로(T5), 규칙마다 멈추면 앞 규칙만 다 보고 뒤 규칙(GENERIC·GAPI)은 늘 빠진다. 받아들인 걸림이 10,000개가 되는 순간 파일 전체를 멈춘다(묶기 전 개수, `.map`은 항목을 합침).
    - S03(T6)도 같은 상한을 둔다(서로 다른 URL을 빽빽이 넣으면 같은 문제가 난다). 이유는 같은 문구, 셈은 S01과 따로 한다.
    - 조건: S01이 멈춘 파일에서 S03 근거 조각을 만들면 ②에 넣을 S01 걸림이 없다. 그러면 ③으로 덮이지 않는 짧은 S01 값(GENERIC 8~19자, URLCRED 비밀번호)이 원문으로 남는다. (a) B가 GENERIC 꼴을 덮는다. URLCRED는 ②에 "주소의 `사용자:비밀번호@`를 `****@`로 바꾼다"(S03 2와 같은 꼴, 선형) 한 줄을 더하면 덮인다. **(b) 2를 고르면 (a) B와 이 한 줄을 함께 골라야 한다.** 그러지 않으려면 S01이 멈춘 파일은 S03도 멈춘다.
    - 안 3은 DB 크기만 막고 검토가 지적한 메모리는 그대로다. 안 1은 위의 1,000만 개 경우를 그대로 둔다.
  - **(c) 안 B 가능, 비용 작음, 100자는 맞다. 다만 뒤쪽을 남긴다**
    - `sources` 이름은 경로라 알아볼 수 있는 부분이 끝(파일 이름)에 있다. 예: `webpack:///./node_modules/…/src/api.ts`. 앞 100자를 남기면 긴 모노레포 경로에서 파일 이름이 잘린다. 권하는 꼴은 `…` + 뒤 100자다.
    - 줄바꿈뿐 아니라 제어 문자(U+0000~U+001F, U+007F)도 공백 하나로 바꾸길 권한다. 탭이나 ESC가 화면·Markdown에 그대로 가지 않는다.
    - 이름에는 ③(긴 덩어리 가리기)을 하지 않는다고 명세에 적는다. 경로의 `/`가 ③의 문자 묶음에 들어 있어 `/node_modules/react/cjs/…` 같은 경로가 `/nod****`가 된다. 지금 구현도 ③을 하지 않는다.
    - 길이는 코드 포인트로 센다. 지문(F-C01)은 `.map` 파일 경로를 쓰므로 바뀌지 않는다.
  - **(d) 안 B 가능, 비용 거의 없음** (T4 시작 전)
    - Windows에서 쓸 수 없는 글자 `< > " | ? *`도 ⓑ에 함께 넣길 권한다. 지금 명세대로면 이 이름들은 쓰다가 OS 오류가 나서 일반 문구 "점검 중 오류가 나서 멈췄습니다"가 된다. U+007F는 Windows가 받으므로 넣지 않는다.
    - 실패 이유의 `<항목>`: 제어 문자를 `\x0A`처럼 눈에 보이는 꼴로 바꾸고 200자에서 자르길 권한다. zip 항목 이름은 65,535바이트까지 될 수 있고 `fail_reason`은 길이 제한이 없는 Text다.
    - T4 구현 주의(명세 아님): `ZipFile.extract()`는 Windows에서 이름의 금지 글자를 몰래 `_`로 바꾼다. ⓑ 검사를 통과한 이름만 직접 써야 한다. 설계가 T4 배정 전에 보안규칙 5장 'zip 항목' 줄에 적는다.
- 계약·폴더·마이그레이션:
  - (a)(c): 레인 사이 계약은 그대로다. 근거 조각은 문자열이고 지문에 들어가지 않는다.
    - 규칙 레인 안의 일 하나: S03(T6)이 ②를 하려면 그 파일의 S01 걸림 범위가 필요하다. 지금 `secrets.scan_file`은 발견만 돌려준다. T6·T8에서 파일 하나의 S01 결과(발견, 걸림 범위, 멈춤 여부)를 S03에 넘기는 모양을 규칙 레인 안에서 정한다(`rules/` 안, 공통 파일 아님).
  - (b): `contracts/engine.py` `SkipReason`에 값 하나(`걸림이 너무 많아 일부만 점검`)를 더하고, `RunRules` 설명의 skipped 줄을 고친다.
    - DB `skipped.reason`은 String(32)이고 문구는 15자라 마이그레이션이 없다.
    - API `SkippedOut.reason`은 str이라 openapi도 바뀌지 않는다.
    - 점검 전체 상한의 안내는 `notices`에 들어가 모양이 그대로다.
    - 반영 때 설계가 계약을 고친다.
  - (d): 그대로(`IntakeFailed.reason` 문구).
  - 새 폴더·라이브러리: 없음.
- 보안:
