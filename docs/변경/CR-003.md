크기: 수정
요청: 검증 T5 첫 검증 '보안' 중간→명세 질문, '재검증' 근거 조각 안 짧은 값, '재검증 2' 낮음(`_collect` 메모리) / T5 보고서 '요청' 문서 / 검증 T5 보안 낮음(`.map` 이름 접두) / 검증 T9 '명세에 없음 1'에서 이어짐 (모두 main 6209b15)

## 무엇을, 왜
T5 검토가 반려하지 않고 넘긴 보안 건이다. 지금 구현은 명세대로지만, 명세대로면 (a) 내보내기 파일(F-E01·E02, 화면 알림 "비밀값은 가려져 있습니다", Markdown 머리 "이 파일에는 비밀값 원문이 없습니다")에 규칙에 걸리지 않은 짧은 비밀번호가 남을 수 있고 (b) 걸림이 빽빽한 큰 파일에서 메모리가 걸림 수에 비례해 는다. (c)(d)는 분석 대상에서 온 이름 글이 거르지 않고 결과에 들어가는 건이다.
CR-002(같은 F-S01의 명확화)를 먼저 반영하고 이 CR의 영향을 다시 찾는다(문서 카드 '한 번에 하나씩').

## 항목별 선택지 (★ = 지금 구현)

**(a) 근거 조각 범위 안의 걸리지 않은 짧은 값 (1절 '근거 조각' ②, 모든 규칙)**
- 안 A ★: 지금대로(S01 걸림과 20자 이상 덩어리만 가린다). 명세에 알려진 한계 한 줄을 적고, 화면 알림·Markdown 머리 문구를 "규칙에 걸린 비밀값은 가려져 있습니다"처럼 고친다
- 안 B: ②에서 S01 걸림에 더해, GENERIC 키워드(`password` 등)가 든 식별자 + `["']?\s*[:=]\s*` 뒤의 값을 길이·자리표시값과 상관없이 `****`로 가린다. 값: 따옴표로 열리면 같은 따옴표 앞까지(범위 안에서 닫히지 않으면 범위 끝까지), 따옴표가 없으면 공백·따옴표·`,;)}]` 앞까지. 근거 조각에서만 가리고 발견은 만들지 않는다
- 안 C: B에 더해 범위 안의 따옴표 글을 모두 `****`로 가린다(가린 값은 그대로)
- 추천 B: 흔한 꼴(`password:"abc12"`, `password = abc12345xyz`)을 막으면서 코드 맥락은 남긴다. C는 가장 안전하지만 근거 조각이 거의 뼈대만 남아 S03 등에서 쓸모가 줄어든다. B로도 `var pw='hunter2'`(`pw`는 키워드가 아님)는 남는다 — 그것까지 막으려면 C
- 설계 확인: B·C 정규식의 선형 시간(GENERIC처럼 키워드를 먼저 찾기), T6(S03)도 같은 `build_snippet`을 쓰므로 함께 적용

**(b) 파일 하나의 걸림 수 상한 (F-S01, 메모리)**
- 안 1 ★: 상한 없음. F-I01의 파일 50MB·합 200MB 상한에 맡기고 명세에 알려진 한계로 적는다. 잰 값(이 CR 작성 때, main 6209b15): 서로 다른 AWS 키 1만 개(210KB) 최대 메모리 7.3MB, 10만 개(2.1MB) 75.6MB — 입력의 약 35배라 빽빽한 50MB 파일은 약 1.7GB로 추정
- 안 2: 파일 하나(`.map`은 항목을 모두 합쳐)에서 받아들인 S01 걸림(묶기 전)이 **10,000개**가 되면 그 파일의 S01을 멈춘다. 그때까지 받은 발견은 남기고, 건너뜀 목록에 그 파일을 이유 `걸림이 너무 많아 일부만 점검`으로 남긴다. 메모리는 위 잰 값으로 약 7MB 안팎
- 안 3: 묶은 뒤 발견 1,000개 상한(넘는 발견은 버리고 같은 알림). DB·화면·내보내기 크기는 막지만 걸림 수에 따른 메모리는 그대로
- 추천 2: 검토가 지적한 원인(걸림 수에 비례)을 직접 막고 DB·화면 크기도 함께 묶인다. 단점: 멈춘 파일은 뒤쪽·뒤 규칙(GENERIC·GAPI 등) 결과가 빠지고, 같은 키가 1만 번 넘게 나오면 횟수가 10,000에서 멈춘다. 숫자(10,000)는 사용자가 정한다
- 설계 확인: 멈추는 단위(규칙마다/파일 전체), 건너뜀 이유를 규칙 함수가 어떻게 돌려주는지(지금 `scan_file`은 발견 목록만 돌려준다 → 계약), S03(T6)도 같은 상한을 둘지

**(c) `.map` `sources` 이름 글 (F-S01 9)**
- 안 A ★: 이름을 그대로 `[<이름>] `으로 붙인다. 줄바꿈·길이 그대로(`sources` `["a\nb.ts"]` → 근거 조각 `[a`↵`b.ts] password:"****"`)
- 안 B: 이름에도 ⑤(줄바꿈 → 공백)를 하고 100자를 넘으면 앞 100자 + `…`. 같은 입력 → `[a b.ts] password:"****"`
- 추천 B: 근거 조각 안에 줄바꿈이 남지 않는다는 ⑤의 뜻과 맞고, 이름 하나가 수 MB여도 조각이 커지지 않는다. 숫자(100)는 사용자가 정한다. Markdown은 F-E02 3이 칸을 200자로 다시 자른다

**(d) zip 항목 이름의 제어 문자 (F-I01 B 2ⓑ)**
- 안 A ★(명세 없음): 정하지 않는다. T4(pending) 구현에 따라 풀다가 OS 오류("점검 중 오류가 나서 멈췄습니다")가 되거나 이름이 그대로 F-C01까지 간다
- 안 B: 조각에 제어 문자(U+0000~U+001F)가 있으면 실패(Windows 이름). Windows는 이 글자를 파일 이름에 쓸 수 없으므로 폴더 입력(F-I01 4)에서는 나올 수 없다
- 추천 B: T4가 시작하기 전이라 비용이 작고, 줄바꿈이 든 경로가 F-C01(CR-002 (9))·화면·내보내기에 들어올 길이 막힌다
- 설계 확인: 보안규칙 5장 'zip 항목' 줄과 맞추기(설계의 파일), 실패 이유의 `<항목>`에 제어 문자가 든 이름을 어떻게 보일지
