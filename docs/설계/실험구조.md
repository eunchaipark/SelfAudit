# 실험 도구 구조 (재설계 2단계 설계)

작성 2026-11-22 · 주인: 설계 · 근거 문서: `docs/01_요구사항.md` 1~8절(D-035~D-038), `ops/계획/재설계-초안.md`, `docs/설계/REA환경.md`

> 이 문서는 **어떻게 만들지**를 정한다. 무엇을 만들지(기능명세 F-B·F-R·F-G·F-M의 처리 규칙·예시)는 문서 역할이 이 틀로 쓴다.
> 모든 값과 결정에 근거를 붙였다(D-038). **[사용자 확인]**이라고 적은 값은 재현율·정밀도·비용을 바꾸는 기준이라, 설계가 추천만 하고 사용자가 정한다(요구사항 8절 3·4·5).
> 새 라이브러리는 쓰지 않는다. 필요해 보이는 곳은 '새 라이브러리 후보'로 따로 적었다(사용자 확인).

## 1. 폴더 구조

```
bench/                      실험 도구 (새로 만듦)
  pyproject.toml            uv 프로젝트. 실행 의존성 없음(표준 라이브러리만), 개발 도구는 backend와 같은 것
  common/                   공통: 계약 타입·검증, 경로·해시 도구 (설계)
  contracts/                기계가 읽는 계약 JSON Schema: answers·findings·run (설계)
  sources/<번들 ID>/        시험 번들의 원본(빌드 전). 가짜 값만 (F-B)
  bundles/<번들 ID>/        시험 번들 = 빌드 결과물. 실험 대상 그대로. 가짜 값만 (F-B)
  answers/<번들 ID>.json    정답지 (F-B)
  targets.json              대상 목록: 번들 ID → 종류(planted·practice)와 위치 (F-B)
  run/                      실행기 (F-R). `prompt.md`(지시문), `mcp-A.json`·`mcp-B.json` 꼴
  score/                    채점기 (F-G)
  measure/                  질문 2 측정 정리 (F-M)
  results/<날짜>/<실행 ID>/ 원자료. 시험 번들·연습앱 결과만 git에 넣는다 (4절)
  tests/<영역>/             테스트 (bundles·run·score·measure·common)
docs/설계/                  설계 메모 (이 문서, REA환경.md)
docs/보고서/                R1 `REA실험.md`, R2 `병렬효율.md`, 그림 `그림/*.svg`
backend/, frontend/         옛 앱. 그대로 둔다(아래). 멈춤
.tools/                     휴대용 Node·REA·Juice Shop 배포본 (git 제외, 스크립트로 만듦)
%LOCALAPPDATA%\SelfAudit-bench\   저장소 밖 실행 폴더: Claude 설정 폴더, 실행마다 대상 복사본, 내 앱 결과 (3·4절)
```

| 정한 것 | 근거 |
|---|---|
| 경로 `bench/bundles`·`bench/answers`·`bench/run`·`bench/score`·`bench/results`, `docs/보고서/` | 요구사항 4절 R1~R5가 이 경로를 결과물 위치로 적었다 |
| `bench/`를 따로 된 uv 프로젝트로 (backend에 넣지 않음) | 옛 앱과 의존성·검사를 섞지 않으려고. 실험 도구는 웹 서버·DB가 필요 없다. backend `pyproject.toml`의 fastapi·sqlalchemy를 끌고 오면 재현에 필요 없는 것이 늘어난다 |
| 실행 의존성은 표준 라이브러리만 (`subprocess`·`json`·`hashlib`·`argparse`) | 새 라이브러리는 사용자 승인이 필요하다(CLAUDE.md). 실행기·채점기가 하는 일(프로세스 실행, JSON 읽기, 세기)은 표준 라이브러리로 된다. 개발 도구 ruff·mypy·pytest·pytest-socket은 backend에서 이미 쓰는 것이라 새 라이브러리가 아니다 |
| `sources/`와 `bundles/`를 둘 다 git에 | 실험 대상은 빌드 결과물이고, 정답지의 줄 번호는 결과물을 가리킨다. 결과물을 커밋해야 빌드 도구 버전이 바뀌어도 대상이 같다(5.1 '대상 같게'). 원본은 '어디에 무엇을 심었나'를 사람이 읽는 근거다 |
| 정답지를 `bench/answers/`에 번들과 떨어뜨림 | 실행기는 번들 폴더만 저장소 밖으로 복사해 준다. 정답지가 번들 폴더 안에 있으면 에이전트가 읽을 수 있다 |
| 실행 폴더를 저장소 밖에 | 저장소 안에서 Claude Code를 돌리면 저장소 `CLAUDE.md`·`.claude/settings.json`(훅)·정답지가 대상 에이전트에게 보인다. 조건 A·B가 같은 것을 보게 하고 정답지를 못 보게 하려고 (3절) |

### 옛 코드: 옮기지 않는다, 조건 C는 나중에 그 자리에서 부른다

**결정**: `backend/`·`frontend/`는 지금 자리에 그대로 두고 '옛 앱(멈춤)'으로 지도·README에 표시한다. `legacy/`로 옮기지 않는다. 조건 C(규칙 검사기, 선택)는 R1 초판 뒤에 만들고, 만들 때는 `bench/baseline/`의 얇은 실행 파일이 `backend/app/rules`(비밀값·소스맵·내부 주소)와 `backend/app/intake`(안전한 풀기)를 **backend의 uv 환경에서** 불러 쓴다(`uv run --project backend python bench/baseline/run_rules.py …` 꼴).

| 근거 | |
|---|---|
| 옮기는 비용이 크고 얻는 것은 '보기에 나뉨'뿐이다 | 옮기면 `ops/checks.json`(검사 폴더 6곳), backend `pyproject`·`uv.lock` 위치, 레인 에이전트 5개의 허용 폴더, `tasks.json` '고칠 파일', 지도·보안규칙·코드규칙의 경로를 모두 같이 고쳐야 한다. 보는 사람이 옛 앱과 실험 도구를 가르는 것은 README·지도 표시로 된다 |
| 멈춘 브랜치가 남아 있다 | T1(review)·T4(반려) 등 옛 태스크 브랜치가 있다. 옮기면 그 브랜치를 병합할 일이 생길 때 모든 파일이 충돌한다 |
| 조건 C가 옛 코드를 그대로 쓴다 | 비밀값·소스맵·내부 주소 규칙은 검토를 거친 코드와 테스트 262개가 있다. 그 자리에서 부르면 기존 검사(`check.py` 서버 검사)가 계속 지킨다 |
| 조건 C를 나중에 | 요구사항 5.1: 조건 C는 선택이고 질문 1의 핵심이 아니다. 사용량을 R3~R5와 첫 실험에 먼저 쓴다 |

다른 안: `git mv backend legacy/backend` — 옛 브랜치를 모두 닫은 뒤(병합 또는 버림), R6 README를 정리할 때 다시 본다. 화면(`frontend/`)은 실험에 쓰지 않지만 검사는 그대로 둔다(멈춘 코드라 깨질 일이 없고, 검사 시간 약 1분).
