## 1. 폴더 구조

```
bench/                      실험 도구 (새로 만듦)
  pyproject.toml            uv 프로젝트. 실행 의존성 없음(표준 라이브러리만), 개발 도구는 backend와 같은 것
  common/                   공통: 계약 타입·검증, 경로·해시 도구 (설계)
  contracts/                기계가 읽는 계약 JSON Schema: answers·findings·run (설계)
  sources/<번들 ID>/        시험 번들의 원본(빌드 전). 가짜 값만 (F-B)
  bundles/<번들 ID>/        시험 번들 = 빌드 결과물. 실험 대상 그대로. 가짜 값만 (F-B)
  answers/<번들 ID>.json    정답지 (F-B)
  targets.json              대상 목록: 번들 ID → 종류(planted·practice)와 위치 (F-B)
  run/                      실행기 (F-R). `prompt.md`(지시문), `mcp-A.json`·`mcp-B.json` 꼴
  score/                    채점기 (F-G)
  measure/                  질문 2 측정 정리 (F-M)
  results/<날짜>/<실행 ID>/ 원자료. 시험 번들·연습앱 결과만 git에 넣는다 (4절)
  tests/<영역>/             테스트 (bundles·run·score·measure·common)
docs/설계/                  설계 메모 (이 문서, REA환경.md)
docs/보고서/                R1 `REA실험.md`, R2 `병렬효율.md`, 그림 `그림/*.svg`
backend/, frontend/         옛 앱. 그대로 둔다(아래). 멈춤
.tools/                     휴대용 Node·REA·Juice Shop 배포본 (git 제외, 스크립트로 만듦)
README.md                   R6 저장소 첫 화면 (문서 역할, 2.6)
저장소 밖 (서로 다른 맨 위 폴더 넷, 3.2·4절):
%LOCALAPPDATA%\SelfAudit-bench-runs\<배치 ID>\<실행 ID>\target\   실행마다 대상 복사본 = 대상 에이전트의 작업 폴더
%LOCALAPPDATA%\SelfAudit-bench-claude\                           실험 전용 Claude 설정 폴더(CLAUDE_CONFIG_DIR, 로그인 정보)
%LOCALAPPDATA%\SelfAudit-private\                                내 앱 대상 목록과 그 원자료
%LOCALAPPDATA%\SelfAudit-bench-archive\                          2MB 넘는 대화 기록(시험 번들·연습앱 것)
```

| 정한 것 | 근거 |
|---|---|
| 경로 `bench/bundles`·`bench/answers`·`bench/run`·`bench/score`·`bench/results`, `docs/보고서/` | 요구사항 4절 R1~R5가 이 경로를 결과물 위치로 적었다 |
| `bench/`를 따로 된 uv 프로젝트로 (backend에 넣지 않음) | 옛 앱과 의존성·검사를 섞지 않으려고. 실험 도구는 웹 서버·DB가 필요 없다. backend `pyproject.toml`의 fastapi·sqlalchemy를 끌고 오면 재현에 필요 없는 것이 늘어난다 |
| 실행 의존성은 표준 라이브러리만 (`subprocess`·`json`·`hashlib`·`argparse`) | 새 라이브러리는 사용자 승인이 필요하다(CLAUDE.md). 실행기·채점기가 하는 일(프로세스 실행, JSON 읽기, 세기)은 표준 라이브러리로 된다. 개발 도구 ruff·mypy·pytest·pytest-socket은 backend에서 이미 쓰는 것이라 새 라이브러리가 아니다 |
| `sources/`와 `bundles/`를 둘 다 git에 | 실험 대상은 빌드 결과물이고, 정답지의 줄 번호는 결과물을 가리킨다. 결과물을 커밋해야 빌드 도구 버전이 바뀌어도 대상이 같다(5.1 '대상 같게'). 원본은 '어디에 무엇을 심었나'를 사람이 읽는 근거다 |
| 정답지를 `bench/answers/`에 번들과 떨어뜨림 | 실행기는 번들 폴더만 저장소 밖으로 복사해 준다. 정답지가 번들 폴더 안에 있으면 에이전트가 읽을 수 있다 |
| 실행 폴더를 저장소 밖에 | 저장소 안에서 Claude Code를 돌리면 저장소 `CLAUDE.md`·`.claude/settings.json`(훅)·정답지가 대상 에이전트에게 보인다. 조건 A·B가 같은 것을 보게 하고 정답지를 못 보게 하려고 (3절) |
| 저장소 밖 폴더를 넷으로 떼어 둠 | 실행 폴더(`…-runs`)의 위쪽 어디에도 설정 폴더(로그인 정보)·내 앱 원자료·다른 배치가 없게 한다. 같은 맨 위 폴더 아래에 두면 `..` 한 두 번이나 넓게 잡은 읽기 규칙 하나로 닿는다(반려 2) |

### 옛 코드: 옮기지 않는다, 조건 C는 나중에 그 자리에서 부른다

**결정**: `backend/`·`frontend/`는 지금 자리에 그대로 두고 '옛 앱(멈춤)'으로 지도·README에 표시한다. `legacy/`로 옮기지 않는다. 조건 C(규칙 검사기, 선택)는 R1 초판 뒤에 만들고, 만들 때는 `bench/baseline/`의 얇은 실행 파일이 `backend/app/rules`(비밀값·소스맵·내부 주소)와 `backend/app/intake`(안전한 풀기)를 **backend의 uv 환경에서** 불러 쓴다(`uv run --project backend python bench/baseline/run_rules.py …` 꼴).

| 근거 | |
|---|---|
| 옮기는 비용이 크고 얻는 것은 '보기에 나뉨'뿐이다 | 옮기면 `ops/checks.json`(검사 폴더 6곳), backend `pyproject`·`uv.lock` 위치, 레인 에이전트 5개의 허용 폴더, `tasks.json` '고칠 파일', 지도·보안규칙·코드규칙의 경로를 모두 같이 고쳐야 한다. 보는 사람이 옛 앱과 실험 도구를 가르는 것은 README·지도 표시로 된다 |
| 멈춘 브랜치가 남아 있다 | T1(review)·T4(반려) 등 옛 태스크 브랜치가 있다. 옮기면 그 브랜치를 병합할 일이 생길 때 모든 파일이 충돌한다 |
| 조건 C가 옛 코드를 그대로 쓴다 | 비밀값·소스맵·내부 주소 규칙은 검토를 거친 코드와 테스트 262개가 있다. 그 자리에서 부르면 기존 검사(`check.py` 서버 검사)가 계속 지킨다 |
| 조건 C를 나중에 | 요구사항 5.1: 조건 C는 선택이고 질문 1의 핵심이 아니다. 사용량을 R3~R5와 첫 실험에 먼저 쓴다 |

다른 안: `git mv backend legacy/backend` — 옛 브랜치를 모두 닫은 뒤(병합 또는 버림), R6 README를 정리할 때 다시 본다. 화면(`frontend/`)은 실험에 쓰지 않지만 검사는 그대로 둔다(멈춘 코드라 깨질 일이 없고, 검사 시간 약 1분).

| `locations` 여러 개 | 같은 문제가 번들 안 여러 곳(결과물과 소스맵 등)에 있으면 한 정답에 위치를 모두 적는다. 그중 하나만 찾아도 그 정답은 찾은 것 | 소스맵에 원본이 들어 있으면 같은 비밀값이 두 파일에 있다. 위치마다 정답을 따로 두면 재현율이 '한 문제를 몇 곳에서 찾았나'가 되어 질문 1('문제를 찾는가')과 어긋난다 |
| `categories` 여러 개 (첫째가 주 범주) | 정답을 만든 사람이 '이 범주로 불러도 맞다'를 적는다(예: 관리 경로가 든 내부 주소 → `internal_address`, `admin_path`) | 범주 경계가 겹치는 문제를 에이전트가 다른 이름으로 불렀다고 틀리게 하면 채점이 '이름 맞히기'가 된다. 정답지에 미리 적어 두면 채점 때 사람 판단이 끼지 않는다(요구사항 R5) |
| `anchor` | 정답을 가르는 짧은 글(가짜 키 값, 경로 글, 플래그 이름). 4~200자, 없으면 `null`. **닻은 번들 안에서 그 정답의 위치에서만 나와야 한다**(F-B07이 센다 — 미끼·다른 정답 위치에 같은 글이 있으면 정답지를 고친다) | 압축된 번들은 한 줄이 수만 자라 줄 번호로는 위치를 가를 수 없다. 결과의 `evidence`에 닻이 들어 있으면 그 문제를 가리킨 것이 분명하다. 우연히 겹치지 않음은 길이가 아니라 '그 위치에서만 나온다'는 시험으로 보장한다 — 4자는 빈 글·한두 글자 같은 실수를 막는 바닥일 뿐이다. 200자: 심을 값 가운데 가장 긴 것은 JWT 꼴 가짜 토큰(약 150자, 추정)이고 경로·키는 100자 안이다. 더 긴 값은 그 안의 고유한 조각을 닻으로 쓴다(확인: F-B07이 200자를 넘는 닻을 거절) |
| `hiding` | `plain`·`split`·`encoded`·`obfuscated`·`sourcemap_only`·`comment`·`config`·`none` | R1의 '난이도별 차이'와 'REA는 숨긴 문제에서 차이를 낼 것'이라는 가설을 숨긴 방법별로 나눠 볼 수 있게 한다(요구사항 R3) |
| `decoys` | 문제처럼 보이지만 문제가 아닌 것(자리표시값, 공개용 키, 테스트 주소 주석 등)과 그 이유 | 정밀도를 '정답지 밖'만으로 재면 헛짚음의 이유를 말할 수 없다. 미끼를 맞히면 이름 붙은 헛짚음이 되어 R1 사례(헛짚은 것 1~2개)가 된다 |
| `complete` | 심은 번들은 `true`(번들 안 문제를 모두 적었다), Juice Shop은 `false`(알려진 것만) | `false`면 정답지 밖 결과가 진짜 문제일 수 있어 정밀도를 '하한'으로만 낸다(2.5) |
| `bundle_manifest_sha256` | 번들 폴더의 파일을 경로 순으로 `<상대 경로>\t<sha256>\n` 줄로 이어 붙인 글의 sha256 | 번들을 다시 빌드해 한 글자라도 바뀌면 줄 번호가 어긋난다. 지문이 다르면 채점기가 멈춘다(F-B04) |
| 경로 꼴 | 번들 맨 위 기준 상대 경로, `/` 구분, 앞의 `/`·`./`, `.`·`..` 마디, `\` 없음(계약의 `pattern`) | 비교를 글자 그대로 하려면 꼴이 하나여야 한다 |
| `origin` | `planted`(직접 심음)·`practice`(Juice Shop) | 실행 원자료의 `target_kind`와 같은 이름을 쓴다. 다른 이름이면 검사(`check_bench.py`)·채점이 둘을 이어 붙일 때 바꾸기 표가 필요해진다(반려 2) |
| 길이 상한 (`planted`·`why` 500자, `bundle_id` 40자, 정답 ID 30자, 경로 300자) | 계약 검사로 막는다 | 측정값이 아니라 **틀린 입력을 막는 울타리**다. 예상 최대의 2~5배로 잡았다: '어디에 무엇을'·'왜'는 한두 문장(약 100~200자), ID는 `easy-1`·`E1-01` 꼴(10자 안), 경로 300자는 Windows 기본 경로 한도 260자보다 조금 길게. 확인: 실제 정답지를 만들다 상한에 걸리면 계약 시험이 실패하고, 그때 설계가 근거와 함께 늘린다 |
| 가짜 값의 꼴 | 서비스 이름이 붙은 실제 키 꼴(AWS `AKIA…`, GitHub `ghp_…`, Stripe `sk_live_…` 등)을 쓰지 않고 이 프로젝트만의 꼴로 만든다. 검사는 4절 | GitHub 비밀 검사(push 막기)는 서비스별 꼴로 찾는다. 그 꼴을 쓰면 push가 막히거나 경고가 생긴다(요구사항 8절 10) |

| 칸 | 정한 것 | 근거 |

| `category` | 8개 + `other`: `secret`(비밀값), `source_map`(소스맵·원본 노출), `internal_address`(내부 주소·개발 서버), `admin_path`(관리 경로), `hidden_route`(숨은 API 라우트), `client_authz`(화면에만 있는 권한 검사), `debug_flag`(디버그 플래그), `vulnerable_library`(옛 버전 라이브러리), `other` | 요구사항 5.1 '대상'에 적힌 문제 종류를 하나씩 범주로 했다('내부 주소·관리 경로'는 둘로 나눔 — 하나는 주소, 하나는 경로라 고치는 방법이 다르다). `other`는 범주 밖 결과를 버리지 않고 받으려고(2.5에서 정밀도에 넣지 않음) |

### 2.4 실행 원자료 (`bench/contracts/run.schema.json`)

`run.json` 하나가 실행 한 번이다. 버전(Claude Code·모델·REA·Node·지시문·계약·MCP 설정의 sha256), 설정(노력·시간·비용 상한·도구·순서 시드·방화벽 규칙 상태), 결과 상태(`ok`·`format_failure`·`timeout`·`budget_exceeded`·`condition_mismatch`·`error`), 지표(시간·토큰·비용·도구 호출 수), 네트워크 기록 수를 담는다.
- 근거: 요구사항 3절 실패 ①(조건이 같지 않음)을 원자료에서 확인할 수 있게, 같아야 하는 것을 모두 실행마다 적는다. ②(다시 계산할 수 없음)를 막으려고 채점에 필요한 것(`findings.json`, 지문)을 같은 폴더에 둔다. 상태를 나눠 두면 '형식 실패가 한 조건에 몰렸나'를 셀 수 있다.
- 실행 ID 꼴: `<대상 ID>-<조건 a·b>-<반복 차례>-<짧은 해시 8자>`(예: `easy-1-a-1-3f2a9c10`), 계약 상한 80자. 근거: 사람이 폴더 이름만 보고 대상·조건·차례를 알 수 있게 하고, 해시로 다시 돌린 실행끼리 이름이 겹치지 않게. 대상 ID 상한 40자 + 나머지 약 15자라 80자는 울타리(2.2 길이 상한과 같은 근거). `mine` 대상은 앞에 `mine-`를 붙인다(`.gitignore` 꼴과 맞추려고, 4절).

### 2.5 채점 규칙 — '맞음' 판정 (F-G02·G03)

결과 하나(f)와 정답 하나(i)가 **후보 짝**이 되는 조건 — 셋 모두:
1. `f.category`가 `i.categories` 안에 있다.
2. `f.file`(정규화: `\`→`/`, 앞의 `./` 지움, 대상 폴더 절대 경로로 시작하면 그 부분 지움)이 `i.locations` 중 하나의 `file`과 글자까지 같다. **[사용자 확인]**
3. 그 위치에서 ㉮ `f.line`이 `[line_start − T, line_end + T]` 안에 있거나 ㉯ `i.anchor`가 있고 `f.evidence` 안에 그대로 들어 있다. **T = 2 [사용자 확인]**.

짝짓기: 후보 짝 가운데 **정답 수가 가장 많아지게 1:1로** 짝짓는다(최대 이분 짝. 같은 수가 되는 짝이 여럿이면 닻 맞음 → 줄 차이 작음 → 결과 차례 → 정답 ID 차례로 골라 늘 같은 답). 짝이 된 결과 = 맞음.
- 동점 차례의 근거: 짝의 **수**(재현율)는 최대 짝이면 차례와 상관없이 같다. 차례는 '어느 결과가 맞음이고 어느 결과가 중복인가'와 위치 정확도만 바꾼다. 그래서 더 확실한 근거(닻) → 더 가까운 줄을 먼저 짝지어 위치 정확도를 낮게 잡지 않게 하고, 나머지는 결과·정답 차례로 정해 같은 원자료면 같은 답이 나오게 한다.

| 값·규칙 | 정한 것 | 근거 |
|---|---|---|
| 경로 정규화·글자 그대로 비교 [사용자 확인] | 위 2번. 대소문자도 가린다 | 번들 안 경로는 대상 폴더의 파일 이름 그대로이고, 에이전트는 도구(Read·Grep·Glob·REA)가 돌려준 경로를 옮겨 쓴다. 대소문자를 무시하면 Windows에서는 같은 파일이지만 정답지 꼴(2.2)과 다른 이름을 맞다고 하게 된다. 다른 안(대소문자 무시)은 R1 한계에 '첫 실험에서 대소문자만 달라 틀린 결과 수'를 세어 보고 바꿀지 정한다 |
| T = 2줄 [사용자 확인] | 줄 번호는 앞뒤 2줄까지 맞음 | 펼친 번들에서 에이전트가 값 줄 대신 선언 줄(`const cfg = {`)이나 다음 줄을 가리키는 일이 있다(추정). 0이면 같은 문제를 찾고도 틀림이 되고, 크면 옆 문제를 잘못 맞힌다. **확인**: 첫 실험 36번을 T = 0·2·5로 채점해 재현율이 얼마나 바뀌는지 R1 한계에 싣는다 |
| 닻 맞춤 [사용자 확인] | 줄이 틀려도 `evidence`에 닻이 있으면 맞음 | 압축 번들은 한 줄이 파일 전체라 줄로는 못 가른다(2.2 `anchor` 근거). 닻은 정답을 만든 사람이 고른 글이라 우연히 맞기 어렵다 |
| 최대 1:1 짝 | 한 결과는 정답 하나만, 한 정답은 결과 하나만 | 결과 하나가 정답 둘을 맞히면 재현율이 부풀고, 같은 정답을 여러 번 내면 정밀도가 부푼다. '가장 많이'로 하면 결과 차례에 따라 숫자가 달라지지 않는다(요구사항 R5 '같은 원자료면 같은 숫자') |
| 중복 [사용자 확인] | 이미 짝이 된 정답을 또 가리킨 결과는 **틀림**(정밀도 분모에 넣음), 따로 '중복 수'로도 보고 | 요구사항 4절 정의가 '맞게 찾은 결과 수 ÷ 낸 결과 수'라 낸 결과는 모두 분모다. 다른 안(중복은 분모에서 뺌)은 같은 것을 여러 번 내는 조건을 벌하지 않는다 |
| `other` [사용자 확인] | 맞음·틀림 어느 쪽에도 넣지 않고(정밀도 분모에서 뺌) 수만 보고 | 정답지는 8개 범주만 다룬다. 범주 밖 결과를 틀림으로 세면 '정답지가 다루지 않는 진짜 문제'를 낸 조건이 손해를 본다. 대신 수를 보고해 `other`로 쏟아 내는지 볼 수 있게 한다 |
| 미끼 | 짝이 안 된 결과가 미끼의 위치(2·3번 조건, 범주는 보지 않음)에 맞으면 '미끼 헛짚음'으로 센다(틀림) | 헛짚음에 이름이 붙어 R1 사례가 된다(2.2 `decoys`) |
| 형식 실패·시간 초과 [사용자 확인] | 그 실행은 재현율 0으로 조건 평균에 넣고, 정밀도는 계산하지 않으며, 상태별 수를 따로 보고 | 빼면 '끝까지 못 낸 실행'이 많은 조건이 유리해진다. 실패도 그 조건의 성능이다. `condition_mismatch`·`error`(실행기 잘못)는 넣지 않고 다시 돌린다 — 조건의 성능이 아니라 실험 장치의 문제라서 |
| 재현율 | 짝이 된 정답 수 ÷ 정답 수 (실행 하나, 번들 하나) | 요구사항 4절 정의 |
| 정밀도 | 맞은 결과 수 ÷ (낸 결과 수 − `other` 수) | 요구사항 4절 정의에 `other` 규칙을 더함 |
| 위치 정확도 | 맞은 결과 중 `f.line`이 `[line_start, line_end]` 안(T 없이)인 비율 | 닻으로만 맞은 결과와 줄까지 맞은 결과를 가른다. '어디인지까지 아는가'를 따로 본다 |

### 2.7 시험 번들 구성과 Juice Shop 정답지 (F-B02·B06·B07)

**심은 번들 6개** (요구사항 R3: 6개 이상, 쉬움·보통·어려움 2개씩):

| `normal-1`, `normal-2` | normal | 압축(한 줄), 파일 이름에 해시 | `split`, `encoded`(base64·16진), `config` | 8~10 | 2~3 |

- 범주: 번들마다 8개 범주(2.3) 가운데 6개 이상, 난이도마다(번들 둘을 합쳐) 8개 모두. 근거: 범주별 재현율을 난이도마다 볼 수 있게. 번들 하나에 모두 넣지 않는 것은 번들끼리 같은 꼴이 되어 둘째 번들이 첫째의 되풀이가 되지 않게.

- 난독화를 직접 만드는 근거: `javascript-obfuscator` 같은 도구는 새 라이브러리다(사용자 확인). 문자열 배열·돌리기·글자 코드 정도는 생성 스크립트로 쓸 수 있다. **새 라이브러리 후보**: javascript-obfuscator(실제 도구가 만든 난독화로 시험하려면).
- **F-B07 검사**(시험): 위 표의 개수(번들 6개, 난이도마다 2개, 정답·미끼 수, 범주 덮기), 정답지가 계약(2.2)에 맞음, 닻 고유성(2.2), 지문이 번들과 같음, 서비스 꼴 키 없음(4절).

**Juice Shop 정답지** (`origin: practice`, `complete: false`):
- 출처: Juice Shop 배포본에 든 공식 도전 과제 목록(`data/static/challenges.yml`, 과제마다 이름·분류·별 1~6개 난이도)과 공식 풀이 안내서(*Pwning OWASP Juice Shop*). 빌드된 화면 번들(`frontend/dist` 쪽)에 **흔적이 있는 과제만** 정답으로 옮기고, 위치(파일·줄·닻)는 번들 레인이 번들을 직접 읽어(검색으로) 적는다 — REA·Claude Code는 쓰지 않는다(위와 같은 근거). 배포본에 `challenges.yml`이 들어 있는지는 확인하지 않았다(추정 — F-B06이 받은 배포본에서 확인하고, 없으면 같은 버전 저장소의 파일을 버전·sha256과 함께 적는다).

- 버전: F-B06이 받는 때의 최신 공식 릴리스를 버전·sha256으로 고정한다(REA와 같은 근거 — 실험 중 바뀌면 원인을 가를 수 없다).

### 2.8 질문 2 — 쪽마다 사용량을 가르는 법 (F-M01)

- **같은 때 돌리지 않는다**: 작업 쌍의 두 쪽(병렬 / `solo-bench`)은 겹치지 않는 시간에 돌리고, 한 쪽이 도는 동안 다른 레인·검토·실험 배치를 돌리지 않는다. 총괄은 그동안 그 쪽을 부르고 기다리는 일만 한다. 근거: `/usage`의 5시간·주간 %는 계정 전체 값이라, 겹쳐 돌면 어느 쪽이 쓴 것인지 가를 수 없다.
- **두 값으로 잰다**: ① 쪽마다 시작·끝에 총괄이 `/usage` %를 읽어 `ops/측정.csv`에 ② Claude Code 세션 기록(설정 폴더 `projects/` 아래 대화 jsonl, 메시지마다 `usage`가 있다 — 추정, F-M01이 실제 파일에서 확인)에서 그 쪽에 속한 세션·에이전트의 토큰 합. ②가 기계가 다시 셀 수 있는 값이고 ①은 사용자가 실제로 쓰는 단위라 둘 다 싣는다.
- 총괄의 몫: 병렬 쪽에서 총괄이 나누기·병합·반려에 쓴 토큰은 병렬 쪽에 넣는다(병렬 방식의 일부). 한 세션 쪽에서는 부르는 메시지 하나만 넣는다. 근거: 총괄의 조율 비용이 바로 병렬 방식의 값이다.
- 차례: 쌍마다 어느 쪽을 먼저 할지 동전 던지기처럼 시드로 정하고 기록한다. 근거: 늘 병렬을 먼저 하면 두 번째 쪽이 같은 명세 이해를 물려받는 등 차례 효과가 한쪽에 몰린다(요구사항 5.2 '같은 작업을 두 번 만들지 않는다'와 같은 걱정).

### 3.2 설정 폴더와 작업 폴더 (`--bare` 없이 두 조건을 같게)

- **실험 전용 Claude 설정 폴더 하나**: `CLAUDE_CONFIG_DIR=%LOCALAPPDATA%\SelfAudit-bench-claude`. A·B가 **같이** 쓴다. 실행기가 **실행마다**(차례로 하나씩 돌므로 겹치지 않는다) 그 안의 `settings.json`을 같은 틀로 쓴다: 훅 없음, 플러그인 없음, 그리고 **거절 규칙**(`permissions.deny`) — 이 설정 폴더 자신, `%LOCALAPPDATA%\SelfAudit-private`, `…-archive`, 저장소 폴더, `~/.claude`, `~/.ssh`, 그리고 **그 실행의 형제 실행 폴더**(같은 배치 폴더 안의 다른 `<실행 ID>` 폴더 하나하나)를 절대 경로로 거절. `…-runs` 맨 위는 거절하지 않는다 — 거절이 허용보다 앞서서 자기 `target`까지 막기 때문이다(반려 3). 허용은 명령줄의 `./**`뿐이다.
  - 지난 실행 폴더는 치운다: 한 실행이 끝나면 원자료를 `bench/results/`(또는 `SelfAudit-private`)로 옮긴 뒤 그 실행 폴더 전체를 지운다. 다음 실행을 시작할 때 배치 폴더 안에 자기 폴더만 있는지 확인하고, 아니면 멈춘다. 그래서 형제 거절 규칙은 보통 비어 있고, 치우기가 실패했을 때의 둘째 층이다.
  - 규칙 꼴: Windows 절대 경로를 Claude Code 규칙에 쓰는 꼴(`Read(//C:/Users/…/**)`와 `Read(//c/Users/…/**)`)은 어느 쪽이 맞는지 확인하지 않았다(추정). 그래서 두 꼴을 모두 쓰고, 문지기 실행(F-R10)에서 **꼴마다** 확인한다: `target` 안에 탐침 파일 둘(`deny-probe-1/x`·`deny-probe-2/x`, 표식 글)을 두고 하나는 `//C:/` 꼴, 하나는 `//c/` 꼴로만 거절해 두면, `./**`가 허용하는데도 읽히지 않은 쪽이 먹히는 꼴이다. 먹힌 꼴을 `run.json`에 적고, 둘 다 안 먹히면 배치를 시작하지 않는다.
  - 거절 규칙의 근거: 허용 꼴(`./**` + `dontAsk`)이 첫 방어이고, 거절 규칙은 그것이 생각과 달리 넓을 때를 위한 둘째 층이다. 거절 목록에는 '새면 가장 아픈 곳'만 적는다(로그인 정보, 내 앱 원자료, 정답지가 있는 저장소, 다른 실행). Claude Code 권한 규칙은 경로를 글자로 맞추므로(형제 폴더의 앞부분만 같으면 통과한 사례가 있었다 — CVE-2025-54794, 반려 3), 규칙만 믿지 않고 3.10의 우회 꼴을 문지기 실행으로 직접 시험한다.
  - 근거: `--bare`는 구독 로그인(OAuth)을 읽지 않아 못 쓴다(도움말). 대신 설정 폴더를 갈라 사용자의 평소 설정(`~/.claude`의 모델 설정·스킬·플러그인 폴더, `~/.claude.json`의 MCP 등록)이 실험에 섞이지 않게 한다. 조건마다 폴더를 따로 두지 않는 것은, 그러면 로그인을 두 번 해야 하고 두 폴더가 어긋날 길이 생기기 때문이다 — A·B의 차이는 MCP 설정 파일 하나로 충분하다.
  - **[사용자 확인·할 일]** 이 폴더로 한 번 로그인해야 한다: `set CLAUDE_CONFIG_DIR=…` 뒤 `claude` → `/login`(사람이 브라우저에서 한 번). 실행기는 로그인 정보 파일을 읽거나 옮기지 않는다(비밀값).
  - 확인할 것(첫 보정 실행에서): 설정 폴더를 바꿨을 때 `~/.claude.json`이 바뀌지 않는지(수정 시각), 시작 이벤트의 인증 출처가 구독인지.
- **작업 폴더는 저장소 밖**: `%LOCALAPPDATA%\SelfAudit-bench-runs\<배치 ID>\<실행 ID>\target\`(번들 복사본)에서 Claude Code를 띄운다. 실행기는 이 폴더의 위쪽 폴더 어디에도 `CLAUDE.md`·`.claude\`가 없음을 확인하고, 있으면 멈춘다. 한 실행이 끝나면 그 `target`을 지운다(다음 실행이 앞 실행 폴더를 볼 수 없게).
  - 근거: 저장소 안에서 띄우면 저장소 `CLAUDE.md`·`.claude/settings.json`(훅)·`bench/answers/`(정답지)가 대상 에이전트에게 보인다. 설정 폴더·내 앱 원자료는 1절처럼 다른 맨 위 폴더에 둔다.
- **문지기 실행 (F-R10, 배치 시작 조건)**: 배치마다 본 실행 전에 A·B 1번씩 짧게 돌린다. 실행기가 작업 폴더 **밖**에 표식 글이 든 파일을 놓아 두고(가짜 형제 실행 폴더, 이름 앞부분만 같은 `target2`, `SelfAudit-private`의 가짜 표식 파일, 설정 폴더, 저장소 `bench/answers/`), 지시문으로 **3.10 표의 꼴마다** 그 파일들을 읽어 보라고 시킨다(Read·Grep·Glob 각각, B에서는 REA 두 도구의 경로 칸으로도). 그리고 위 '규칙 꼴' 탐침 둘. **꼴마다 대화 기록과 결과 어디에도 표식 글이 없고, 그 시도의 거절(권한 거절·거르개 오류) 기록이 남아야** 통과다. 하나라도 새면 배치를 시작하지 않고 총괄에 알린다. 에이전트가 시도하지 않은 꼴(거절 기록 없음)도 실패로 본다 — 시험을 건너뛴 것과 막힌 것을 가르려고.
  - 근거: `Read(./**)`의 뜻·거절 규칙·거르개 ⑷가 실제로 맞물리는지는 문서로 확인할 수 없어 실행으로 본다(반려 2). 배치마다 하는 것은 Claude Code가 자동으로 바뀌거나 설정이 어긋나도 잡으려고(그래서 자동 업데이트도 끈다). 비용은 보정 배치에서 잰다(3.5, 짧은 실행 2번).
- **허용 목록 환경**: Claude Code도 허용 목록 환경으로 띄운다(`SystemRoot`·`SystemDrive`·`windir`·`ComSpec`·`PATHEXT`·`NUMBER_OF_PROCESSORS`·`PROCESSOR_ARCHITECTURE`·`OS`·`USERPROFILE`·`APPDATA`·`LOCALAPPDATA`·`TEMP`·`TMP`, `PATH`=System32만, `CLAUDE_CONFIG_DIR`, `DISABLE_AUTOUPDATER=1`). REA는 거르개가 이보다 더 좁은 환경으로 띄운다(`REA환경.md` 6절).
  - 근거: 사용자 환경의 토큰·키 변수가 대상 에이전트나 REA에 가지 않게. 홈 폴더는 Claude Code가 로그인·설정을 찾는 데 필요할 수 있어 진짜 값을 넘긴다(추정 — `CLAUDE_CONFIG_DIR`만으로 충분한지 첫 보정 실행에서 확인하고, 되면 실행 폴더 안 빈 폴더로 돌린다).

### 3.3 명령줄 꼴

```
프로그램: %APPDATA%\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe   (claude.cmd를 거치지 않음 — 셸 없이)
작업 폴더: %LOCALAPPDATA%\SelfAudit-bench-runs\<배치 ID>\<실행 ID>\target
인자:
  -p "<prompt.md 내용>"
  --model <모델 전체 ID> --effort <노력>                       [사용자 확인]
  --output-format stream-json --verbose                         # 대화 전체(사례용)와 마지막 result(비용·토큰·결과)
  --json-schema "<findings.schema.json 내용>"
  --tools "Read,Grep,Glob"
  --allowedTools "Read(./**) Grep(./**) Glob(./**) mcp__rea__analyze_javascript_application mcp__rea__audit_release_exposure mcp__rea__trace_javascript_semantics mcp__rea__trace_application_feature"
  --permission-mode dontAsk
  --strict-mcp-config --mcp-config <실행 폴더>\mcp.json         # A: {"mcpServers": {}}  B: REA환경.md 6절
  --setting-sources user --disable-slash-commands --no-session-persistence
  --max-budget-usd <비용 상한>                                  [사용자 확인]
끝내기: 시간 상한을 넘으면 taskkill /T /F (프로세스 나무째) → 상태 timeout
```
- 근거: `stream-json`은 도구 호출과 결과를 줄마다 남겨 R1 사례(실제 결과 조각)를 원자료에서 꺼낼 수 있고, 마지막 `result` 줄에 시간·토큰·비용·구조화 결과가 있다(Claude Code 출력 형식). `-p`의 작업 폴더 신뢰 창은 건너뛴다(도움말) — 그래서 작업 폴더를 실행기가 만든 복사본으로만 쓴다. `--max-budget-usd`는 "API 호출에 쓸 최대 금액"이라 구독에서 어떻게 세는지는 확인하지 않았다(추정: 같은 계산으로 끊는다. 첫 보정 실행에서 작은 상한으로 확인).

### 3.4 조건 확인 (F-R05)

stream-json의 첫 `system`(init) 줄을 읽어 기대와 맞춘다. 다르면 그 실행은 `condition_mismatch`로 버리고 채점하지 않는다(다시 돌린다).
- 도구 목록 = A: `Read`·`Grep`·`Glob` / B: 그것 + `mcp__rea__` 4개 (그 밖이 하나라도 있으면 불일치)
- MCP 서버 = A: 없음 / B: `rea` 하나, 연결됨
- 모델 = 요청한 전체 ID, 권한 모드 = `dontAsk`
- 근거: 실패 ①(조건이 같지 않음)을 실행 뒤가 아니라 실행마다 기계가 잡는다. init 줄의 정확한 필드 이름은 첫 보정 실행에서 확인해 F-R05 명세 예시에 넣는다.

### 3.5 1번 비용 재는 법 (F-R08)과 상한

1. **보정 배치** (첫 실험 전): ㉮ 빈 실행 A·B 1번씩 — 대상 없이 "빈 결과를 내라"는 지시. 시스템 프롬프트·도구 설명의 고정 비용과 A·B 차이(REA 도구 설명 8KB)를 잰다. 대상을 점검하는 실행이 아니라 요구사항 5.1의 '처음 2~3번'에 세지 않는다 ㉯ **대상 실행 2~3번**: 쉬움 번들 하나로 A·B 1번씩, 그리고 B가 A의 2배 넘게 들면 어려움 번들 B 1번을 더한다(어려움에서 REA 응답이 얼마나 커지는지 — MCP 응답이 작은 번들에서도 52만 바이트였다, `REA환경.md` 6절) ㉰ 문지기 실행(3.2) 2번의 비용도 같이 적는다. 근거: 요구사항 5.1 '처음 2~3번을 돌려 1번 비용을 잰 뒤 나머지를 정한다'를 ㉯로 맞추고, ㉮·㉰는 그 숫자를 가르는 데 쓴다.
2. 실행마다 `result` 줄의 `total_cost_usd`, `usage`(입력·출력·캐시 생성·캐시 읽기 토큰), `duration_ms`, `duration_api_ms`, `num_turns`를 `run.json`에 옮긴다.
3. **구독 사용량 %**: 총괄이 보정 배치 앞뒤에 `/usage`의 5시간·주간 %를 읽어 `ops/측정.csv`에 적는다(사람이 읽는 값 — CLI에서 기계가 읽는 길은 확인하지 못했다). `total_cost_usd`는 API 값으로 친 추정이라 구독에서 실제로 깎이는 %와 다를 수 있어 둘 다 남긴다.
4. 36번 사용량 추정 = (㉯의 A·B 평균 %) × 18 × 2, 난이도별 크기 차이는 번들 크기 비로 늘린다(추정). 하룻밤 남은 %에 들어가는지 총괄이 정한다(요구사항 8절 6).
5. **상한 [사용자 확인]**: 시간 = 보정 ㉯ 실행 중 가장 긴 것의 3배(분 단위로 올림, 적어도 10분), 비용 = 보정 ㉯ 중 가장 큰 것의 3배. 두 조건에 같은 값.
   - 근거: 상한은 조건의 성능을 자르지 않을 만큼 넉넉해야 하고(어려움 번들은 쉬움보다 오래 걸린다), 멈춘 실행이 밤 전체를 쓰지 않게 막아야 한다. 3배는 보정 실행이 쉬움 번들 위주라 어려움에서 더 걸릴 여유다(추정). '적어도 10분'은 REA 분석 하나가 자기 기본 상한(`--analysis-timeout-ms` 300,000 = 5분, `REA환경.md` 5절)까지 걸려도 그 뒤 에이전트가 결과를 정리할 시간이 남게 잡은 값이다. 상한에 걸린 실행 수를 R1에 보고하고, 한 조건만 많이 걸리면 상한을 올려 다시 돈다.
   - **비용으로 거는 근거(요구사항은 '토큰 상한')**: Claude Code CLI에는 토큰 수로 끊는 인자가 없고 `--max-budget-usd`(금액)만 있다(2.1.119 도움말). 금액은 토큰 수 × 모델 값으로 셈하므로 같은 모델이면 토큰 상한과 같은 일을 한다. 토큰 수는 실행마다 그대로 기록한다(2.4). 요구사항 글은 문서 역할이 고친다(6절).

### 3.6 차례와 동시 실행

- 실행 목록(대상 × 조건 × N)을 시드로 섞어 하나씩 돌린다. 시드는 `run.json`(`order_seed`)에.
  - 근거: 시간에 따라 바뀌는 것(서버 부하, 사용량 한도에 가까워짐)이 한 조건에 몰리지 않게. 차례대로(A 전부 → B 전부) 돌리면 그 차이가 REA 차이처럼 보인다.
- 동시에 돌리지 않는다. 근거: 동시 실행은 요청 한도와 CPU를 나눠 써 시간 지표를 흔들고, 한 실행의 REA 자식과 다른 실행의 것이 섞여 ㉡ 기록을 가르기 어렵다.

### 3.7 네트워크 기록 (F-R07)

- ㉠은 거르개가 REA를 띄울 때 넣고, ㉡은 실행기가 Claude Code 나무 안에서 이미지 경로가 `<ROOT>\.tools\node\node.exe`인 프로세스와 그 자손만 본다(Claude Code 자신의 API 연결은 실험의 일부라 뺀다). 방화벽 규칙(사용자 확인)을 두었으면 `Get-NetFirewallRule`로 상태를 `settings.firewall_rule`에.
- 조건 A에도 ㉡을 돌린다(REA가 없으니 기록 0이어야 한다 — 감시가 헛것을 잡지 않는지 보는 대조).
- 기록이 하나라도 있으면(막은 것·끝점) 그 배치를 멈추고 총괄에 알린다. 근거: 외부 호출은 Claude Code의 모델 호출과 REA가 하는 호출만 허용됐고(D-036), REA의 바깥 연결은 지금까지 기록된 적이 없어 생기면 원인을 먼저 봐야 한다.

### 3.8 원자료 폴더

`bench/results/<YYYY-MM-DD>/<실행 ID>/` — `run.json`, `findings.json`(검증한 결과, 경로는 대상 기준 상대 경로로 바꿈), `transcript.jsonl`(stream-json, 실행 폴더 절대 경로는 `<RUN>`으로 가림), `netguard.jsonl`, `netstat.json`.
- `transcript.jsonl`이 2MB를 넘으면 git에 넣지 않고 저장소 밖(`%LOCALAPPDATA%\SelfAudit-bench-archive\`)에 두고 `run.json`에 sha256만 남긴다 **[사용자 확인]**. 근거: 숫자를 다시 계산하는 데는 `run.json`·`findings.json`이면 된다(R5). REA MCP 응답은 작은 번들에서도 한 번에 52만 바이트였다(`REA환경.md` 6절) — 36번이면 수십 MB가 저장소에 쌓인다. 2MB는 GitHub가 경고하는 파일 크기(50MB)와 저장소 권장 크기(1GB)보다 훨씬 작게 두어, 실험을 늘려도 저장소가 무거워지지 않게 한 값이다(추정). **확인**: 보정 배치(3.5)의 대화 기록 크기를 재고, '36번 × 평균 크기'가 100MB를 넘거나 2MB 아래 기록이 거의 없으면(사례를 뽑을 기록이 저장소에 안 남음) 값을 사용자에게 다시 올린다. R1 사례에 쓸 조각은 크기와 상관없이 F-G06이 보고서로 옮긴다.

- 계획 파일(`bench/run/plans/*.json`)에 대상 ID 목록·조건·N·모델·노력·상한·순서 시드를 적는다. 근거: 요구사항 R4 '명령 하나로 다시 돌릴 수 있다' — 바꿀 값을 명령줄이 아니라 커밋된 파일에 두면 같은 계획을 누구나 다시 돌릴 수 있고, 계획 파일의 sha256을 `run.json`에 남긴다.
- 시험(F-R09): 정해진 stream-json을 내놓는 가짜 `claude.exe`(시험용 스크립트)로 작은 계획을 두 번 돌려 두 원자료로 낸 채점 숫자가 같은지 본다. 실제 모델을 부르는 다시 돌리기는 결과가 흔들리는 것이 실험의 일부라 '같은 숫자'가 아니라 '같은 방법'을 확인한다.

## 4. 원자료의 비밀값 원문 — 무엇을 git에 넣나

REA 출력과 에이전트 결과(`evidence`)에는 대상 안의 글이 그대로 들어간다(`REA환경.md` 5절). 그래서 대상 종류로 저장 위치를 가른다.

| 대상 종류 (`target_kind`) | 무엇 | 원자료 위치 | git |
|---|---|---|---|
| `planted` | 직접 만든 시험 번들. 가짜 값뿐 | `bench/results/<날짜>/<실행 ID>/` | 넣는다 |
| `practice` | OWASP Juice Shop 공식 배포본 (공개 MIT 코드) | 같음 | 넣는다 |
| `mine` | 내 실제 앱 | `%LOCALAPPDATA%\SelfAudit-private\results\<날짜>\mine-<실행 ID>\` (저장소 밖, 실행 폴더들과 다른 맨 위 폴더) | **넣지 않는다** |

- 근거: 시험 번들은 공개 저장소에 올라가도 되게 처음부터 가짜 값으로 만든다(요구사항 6절). Juice Shop은 이미 공개된 코드라 조각이 원자료에 남아도 새로 드러나는 것이 없다(R1 사례에 쓸 때 출처를 적는다). 내 앱은 진짜 비밀값이 있을 수 있다(CLAUDE.md '하지 않는 것'). 내 앱 결과를 보고서에 쓸 때는 R5가 낸 숫자(재현율 등)만 옮기고 원문 조각은 옮기지 않는다.

**세 겹으로 막는다**:

| 겹 | 무엇 | 근거 |
|---|---|---|
| ⑴ 실행기 (F-R06) | `target_kind`가 `mine`이면 출력 폴더를 저장소 밖으로 고정하고, 저장소 안 경로를 주면 거절한다. 내 앱 목록도 저장소 밖(`%LOCALAPPDATA%\SelfAudit-private\targets.json`)에만 둔다. 조건 B에서는 거르개 ⑷가 REA 경로 칸을 그 실행의 target 안으로 가둔다(`REA환경.md` 6절) — 다른 실행·내 앱 원자료를 REA로 읽어 대화 기록에 싣는 길을 막는다 | 잘못 쓰는 길을 처음부터 없앤다 |
| ⑵ `.gitignore` | `bench/private/`, `bench/results/**/mine-*/` | ⑴이 틀려 저장소 안에 생겨도 `git add`에 걸리지 않게 |
| ⑶ 검사 `ops/scripts/check_bench.py` (`check.py` '실험자료') | 작업 폴더와 **git 색인(staged 내용 포함)** 둘 다 본다. 허용 꼴만 통과: `bench/results/` 아래는 `<날짜>/<실행 ID>/<허용 이름 5개>`와 `README.md`뿐, 실행 폴더마다 `run.json`이 있고 `target_kind`가 planted·practice이며 `bench/targets.json`에 같은 종류로 있고, **`bundle_manifest_sha256`이 그 대상 정답지의 지문과 같다**(종류 글만 믿지 않고 대상 번들 자체가 같은지 본다). `bench/targets.json`의 종류도 planted·practice뿐. 그리고 `bench/` 아래 글 파일에 서비스 꼴 키(AWS·GitHub·Slack·Stripe·Google·Anthropic·OpenAI 키, 개인 키 머리)가 없다 — 찾으면 값은 찍지 않고 꼴 이름과 줄만 찍는다 | ⑴·⑵가 모두 틀려도 커밋 전에 검사가 잡는다. 서비스 꼴만은 막을 꼴 목록인데, GitHub 비밀 검사가 서비스별 꼴로 push를 막으므로 피할 것도 그 꼴이기 때문이다(요구사항 8절 10). 가짜 값은 이 프로젝트만의 꼴로 만든다(2.2) |

검사 시험(scratchpad에서 16가지): bench 없음·정상·정상(git 색인) → 통과 / `mine` 결과, 지문이 다른 번들을 planted로 적은 결과, 정답지 없음, 허용 밖 파일 이름, `run.json` 없는 실행 폴더, `targets.json`의 `mine`, **색인에만 올린 키(작업 폴더는 깨끗)**, **작업 폴더에서 지웠지만 색인에 남은 mine 결과**, **색인의 `run.json`만 mine(작업 폴더 버전은 planted)**, **색인의 `targets.json`만 mine**, AWS·OpenAI 꼴 키 → 모두 걸림. OpenAI 꼴이 아닌 것(경계 없는 `xsk-…`) → 통과.
- `run.json`·`targets.json`·정답지는 작업 폴더 버전과 색인 버전을 **각각** ㉡·㉢ 규칙으로 본다(반려 3). 커밋에 들어가는 것은 색인 버전이고, 작업 폴더 버전만 보면 색인에만 올린 내용이 빠진다.
- 느린 꼴: OpenAI 꼴 정규식(`sk-…{20,}T3BlbkFJ`)은 뒤 글자 때문에 `sk-`가 많은 줄에서 제곱으로 느려졌다(반려 2: 12만 자 6.6초). 키 글자 덩어리를 한 번씩만 보는 검사로 바꿨다. 다른 꼴은 뒤 조건이 없거나 길이가 정해져 있다. 1MB 줄 8가지(`sk-`·`ghp_`·`xoxb-`·`AKIA`·`AIza`·`sk-ant-` 반복, `-` 덩어리 등)에서 줄 하나 0.07~0.17초.
- 커밋 훅은 두지 않는다: git 훅은 저장소에 실려 오지 않아(각자 `.git/hooks`) 지킬 수 없는 약속이 된다. 대신 `check.py`가 커밋 전 규칙(CLAUDE.md)이고, 총괄이 병합 전에 돌린다.
- 한계: 이 프로젝트만의 꼴로 만든 가짜 값이 진짜인지 가짜인지는 검사가 가르지 못한다. 시험 번들을 만드는 레인(F-B)이 값을 난수로 만들고(진짜 키를 옮기지 않음), 정답지 `planted`에 '가짜(생성)'라고 적는다.
- `GitHub 비밀 검사`가 이 프로젝트만의 꼴(일반 고엔트로피 글)도 잡는지는 모른다(추정: push 막기는 서비스 꼴만, 일반 글은 알림만). 확인: 첫 시험 번들을 올린 push에서 막힘·알림이 있는지 총괄이 본다.
