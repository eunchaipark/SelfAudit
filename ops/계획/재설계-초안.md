# 재설계 초안 — REA 중심 (총괄, 2026-11-21 밤, 사용자 확인: "진행하고 … 뭘 보여줘야하는지 … 어떤 결과물을 내야하는지 잘 적어야해")

## 0. 한 줄
"같은 AI 에이전트(Claude Code)가 내 웹앱 빌드 결과물을 점검할 때, 역설계 도구 REA를 쥐여 주면 보안 문제를 더 많이·더 정확히 찾는가"를 숫자로 보이고, 그 실험 도구를 만드는 과정에서 "내 병렬 작업 방식이 한 세션보다 효율적인가"를 같이 잰다.

## 1. 보여 줄 것 (포트폴리오에서 보는 사람이 얻어 가는 것)
보는 사람이 README 첫 화면과 보고서 두 개만 읽고 아래 다섯 가지를 알 수 있어야 한다.
1. **질문**: REA가 AI 보안 점검을 낫게 하는가 / 병렬 방식이 낫는가
2. **방법**: 무엇을 같게 하고 무엇만 바꿨는지(모델·지시·대상·시간 상한은 같고 REA만 다름), 정답지는 어떻게 만들었는지
3. **결과 숫자**: 조건별 찾은 비율(재현율)·맞게 찾은 비율(정밀도)·시간·비용, 난이도별 차이, 반복 N번의 범위(최소~최대)
4. **사례**: REA가 있어야만 찾은 것 2~3개, REA가 헛짚은 것 1~2개 — 실제 결과 조각과 함께
5. **결론과 한계**: 한 문단 결론("REA를 쥔 Claude Code는 어려움 단계 비밀값 재현율이 33% → 83%, 정밀도는 비슷, 비용은 2.1배" 꼴), 이 실험이 말하지 못하는 것(대상 수, 웹 번들만, 모델 하나)

**보여 줄 것이 이 다섯인 근거**: 질문·방법·결과·사례·한계는 실험 보고의 최소 구성이다. 하나라도 빠지면 보는 사람이 결과를 믿을 근거가 없다(방법이 없으면 공정했는지, 사례가 없으면 숫자가 무엇을 센 것인지, 한계가 없으면 어디까지 말할 수 있는지 모른다). 보고서를 둘로 나눈 것은 질문이 둘이고, 재는 대상(점검 결과 / 만드는 과정)이 달라서다.

### 성공의 정의와 근거
- **성공 = 두 질문에 '공정하게 잰 숫자 + 그 숫자가 나온 이유'로 답한 것.** "REA가 별 차이 없다"나 "오히려 나쁘다"도 성공이다.
- 근거: 이 프로젝트의 목적은 REA가 낫다고 **보이는 것**이 아니라 낫는지 **알아내는 것**이다(사용자 질문이 "높일 수 있는가"). 'REA가 이기면 성공'으로 정하면 시험 번들을 REA에 유리하게 만들 유혹이 생겨 결과를 믿을 수 없게 된다. 그래서 성공은 결과의 방향이 아니라 **잰 방법의 공정함과 재현성**으로 정한다.
- 실패 = 조건이 같지 않았거나(모델·지시·대상이 다름), 숫자를 다시 계산할 수 없거나, 차이의 이유를 사례로 설명하지 못한 것.

## 3. 질문 1 실험 설계
| 조건 | 무엇 |
|---|---|
| A | Claude Code — 파일 읽기·검색 도구만 (REA 없음) |
| B | Claude Code + REA (MCP 또는 CLI) |
| C (선택) | 사람이 짠 규칙 검사기 — AI 없는 바닥값. 기존 비밀값·소스맵·내부 주소 점검 코드 |

- 대상: ① 시험 번들 — 평문·나눠 쓴·난독화된 비밀값, 소스맵, 내부 주소·관리 경로, 숨은 API 라우트, 화면에만 있는 권한 검사, 디버그 플래그, 옛 버전 라이브러리. 쉬움·보통·어려움 ② OWASP Juice Shop 공식 배포본(사용자 허락 2026-11-21) — 실행하지 않고 빌드 결과물만
- 같게: 모델, 지시문, 시간·토큰 상한, REA 버전 고정, 같은 대상을 조건마다 N번(처음 N=3)
- 결과 형식: 정해진 JSON(종류·파일·위치·근거·확신) → 채점기
- 첫 실험: 번들 6개 × A·B × 3번 = 36번 (사용자 허락: 밤사이 자동 실행 가능)
- 근거: A·B만 두고 나머지를 같게 하는 것은 차이를 REA 하나로 돌리려고(바꾸는 것이 둘이면 어느 쪽 때문인지 모른다). N=3은 범위(최소~최대)를 보고 튀는 값 하나를 알아볼 수 있는 가장 작은 수다. 사용량이 N에 비례해서 3으로 시작하고, 흔들림이 크면 늘린다. 36번이 하룻밤 사용량에 들어가는지는 아직 모른다(추정) → 처음 2~3번을 돌려 1번 비용을 재고 나머지를 정한다. 조건 C(규칙 검사기)는 'AI가 사람이 짠 규칙보다 나은가'라는 바닥값을 주지만 질문 1의 핵심이 아니라 선택이다

## 4. 질문 2 실험 설계
- R3~R5를 만드는 작업 중 비슷한 크기의 작업 쌍을 고른다. 하나는 병렬(레인 + 검토 + 총괄), 하나는 한 세션이 나누지 않고 만든다(같은 명세, 같은 검사).
- 둘 다 병합 뒤 같은 독립 검토(보안·명세)를 한 번 더 돌려 '남은 결함'을 센다.
- 기록: 시작·끝 시각, 사용량(5시간·주간 %p), 반려 수, 검토가 잡은 결함(심각도별), 남은 결함, 다시 한 일. `ops/측정.csv`에 칸을 늘린다.
- 지난 기록(T2~T19, 검증 13개)은 '병렬' 쪽 참고 사례로 쓴다(예: T6 값 칸 비밀번호 노출, T4 bz2 압축 폭탄을 검토가 잡음).
- 근거: 같은 작업을 두 번 만들면 두 번째가 첫 번째를 보고 배워 공정하지 않다 → 같은 작업이 아니라 '비슷한 크기의 다른 작업' 쌍으로 한다. 크기는 명세 예시 수·바뀔 파일 수로 맞춘다(완벽히 같을 수 없음은 한계에 적는다). 지난 기록만으로는 비교 대상이 없어 '병렬이 낫다'를 말할 수 없어서 비교군을 만든다(사용자 선택)

## 5. 환경 (사용자 허락 2026-11-21)
- Node: nodejs.org 공식 휴대용 zip(22.23.4 이상 또는 24.22.1 이상)을 저장소 안 `.tools/`(git에 안 올림)에 받아 REA 전용으로만 쓴다. 지금 Node 22.19.0은 그대로.
- REA: `rea-agents`를 버전 고정으로 설치. 먼저 이 PC(Windows)에서 `analyze-javascript-application`이 도는지 시험. 안 되면 대안(WSL)을 보드에 올린다.
- 외부 AI 호출은 이 실험에서만 허용(대상은 내 앱·허용 연습앱·직접 만든 시험 번들뿐).
- 근거: 휴대용 Node는 관리자 권한 없이 깔리고(사용자가 자는 동안 권한 창이 뜨면 멈춘다) 지금 화면 빌드에 쓰는 Node 22.19.0을 건드리지 않는다. REA 버전 고정은 REA 문서가 '빨리 바뀐다'고 해서, 실험 중 버전이 바뀌면 결과 차이가 REA 버전 때문인지 알 수 없어서다. Windows 시험을 먼저 하는 것은 문서에 Windows에서 JS 분석이 되는지 적혀 있지 않아서다

## 기준·결정의 근거 규칙 (사용자 2026-11-21)
