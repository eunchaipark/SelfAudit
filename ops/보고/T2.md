## 한 것
앱마다 점검 기록을 최신순으로 보여 주고(완료가 아니면 점수·개수는 `-`), 앱 목록에 앱마다 가장 최근 `완료` 점검의 점수와 시각을 보여 준다(F-P02). 앱을 지우면 그 앱의 점검·발견·건너뜀·참고·남은 격리 폴더가 함께 지워지고 지운 점검 수를 돌려준다. `confirm=true`가 없거나 다른 값이면 400으로 거부하고 아무것도 지우지 않는다. 진행 중 점검이 있으면 "점검이 끝난 뒤 지울 수 있습니다"로 거부한다(F-P03 1·3·4).
엔진(정렬·완료만 점수·앱별 최근 완료·진행 중 판정) → repo·service·api(`GET /apps`, `GET /apps/{id}`, `GET /apps/{id}/scans`, `DELETE /apps/{id}?confirm=true`) → SCR-01 화면 순서로 만들었다.

- 명세 절차에 단계를 더함: F-P03 4 진행 중 확인을 두 번 한다. 먼저 점검 상태를 읽어 거부하고, 지울 때 "진행 중 점검이 없을 때만 앱을 지운다"를 한 SQL 문장으로 한다. 확인한 뒤 그 앱의 점검이 막 시작되면 지우지 않고 같은 문구로 거부한다. 진행 중 점검을 지우지 않게 하려는 것이다
- 명세 절차에 단계를 더함: 남은 격리 폴더를 지우지 못하면(Windows 파일 잠금 등) 로그(점검 ID·예외 종류만)를 남기고 지우기는 성공으로 돌려준다. DB는 이미 지웠고, 남은 폴더는 서버가 다음에 시작할 때 지운다(F-I01 12)

- 앱 목록의 이름순은 casefold한 이름(중복 검사 열쇠)의 코드 포인트 순이다(`alpha` → `Juice Shop` → `내 블로그`)

## 요청
1. 설계: `backend/tests/core/test_security.py::test_빈_API는_501_한가지_형식`이 `GET /api/v1/apps`로 501을 시험한다. T2가 이 API를 채워서 실패한다. 아직 빈 다른 API(예: `GET /api/v1/scans/1`, T15 전까지)로 바꾸거나, 빈 API가 다 없어지면 테스트를 지워 달라
2. 총괄(병합 뒤): `backend/openapi.json` 다시 만들기(`uv run python -m app.contracts.export_openapi` → `npm run gen:api`). 차이는 `app_id` 경로 인자 3곳의 `minimum`·`maximum`뿐이다
3. 설계: 쿼리 `confirm: Literal[True]`는 `?confirm=true`를 받지 못한다(pydantic의 Literal은 글 `"true"`를 참으로 바꾸지 않아 400이 된다). `scans/api.py`의 `delete_scan`(T15)도 같다. `apps/api.py`의 `Confirm`(정확히 `"true"`만 참으로 읽는 BeforeValidator, 계약 스키마 `const: true`는 그대로)을 `core/deps.py`의 공용 `ConfirmQuery`로 옮기고 두 레인이 그것을 쓰게 해 달라
4. 설계·총괄(T15와 맞추기): 점검의 남은 격리 폴더 지우기를 `apps/service.py`의 `remove_work_dirs(work_dir, scan_ids)`로 만들었다. T15의 점검 지우기도 같은 일을 한다. 중복이 되면 공용 함수(예: `core/`나 `scans/`)로 옮길지 정해 달라. 지우는 차례(진행 중이면 거부 → DB 지우기 → 커밋 → 폴더 지우기, 폴더를 못 지우면 로그만)도 맞추면 좋다

## 다음 세션이 알아야 할 것
- 점검 행은 `engine.ScanRecord`로 읽는다(`repo.RECORD_COLUMNS`, 발견을 읽지 않는다). 점검 기록 정렬·완료만 점수는 엔진에 있다
- 앱 지우기는 ORM cascade가 아니라 `delete(App)` 한 문장과 DB의 `ON DELETE CASCADE`(PRAGMA foreign_keys=ON)로 지운다. ORM `session.delete(app)`은 발견 수만큼 객체를 읽어 느리다
- 테스트 도우미 `tests/apps/conftest.py`의 `add_app`·`add_scan`은 점검 흐름 없이 점검 행을 넣는다

## 문제와 개선
- 방법론: 배정문은 ID를 `IdPath`로 받으라 했지만 그러면 생성 파일 `openapi.json`이 바뀌어 검사 '계약'이 레인 브랜치에서 반드시 실패한다 → 공통 계약을 바꾸는 설계 변경(IdPath)은 설계가 빈 API까지 미리 IdPath로 바꾸고 openapi를 다시 만들어 두거나, 배정문에 '계약 검사 실패는 예상됨'을 적어 둔다
- 방법론: 공통 테스트(`test_빈_API는_501`)가 특정 레인 API를 빈 것의 예로 써서 그 레인이 기능을 채우면 깨진다 → 공통 테스트는 레인 API에 기대지 않는 경로(테스트 전용 라우터 등)로 시험한다
- 프로젝트: 계약 뼈대의 `confirm: Literal[True]` 쿼리가 실제 요청 `?confirm=true`를 받지 못했다. 뼈대 단계에서 빈 API의 입력 검증을 한 번 불러 보는 테스트가 없었다 → 설계가 뼈대 API를 만들 때 경로·쿼리 인자 파싱만 보는 테스트를 함께 둔다
- 방법론: Bash에서 `cd … && python - <<EOF` 같은 여러 줄 명령이 worktree 격리 검사에 막혀 Edit 도구로 다시 했다 → 레인 카드 '공유 자원'에 "여러 줄 스크립트는 scratchpad 파일로 쓰고 한 줄로 실행"을 적어 둔다
