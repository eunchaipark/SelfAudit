## 반려 고침
- **[중간 1] S01-JWT 제곱 시간**: JWT를 `_SIMPLE`에서 빼 `_jwt_candidates`로 옮겼다. 시작 자리 `eyJ`는 `str.find`로 찾고, 명세 정규식과 같은 뜻의 먹보 한정자 식(`{5,}+` 등)을 그 자리에서만 맞춘다. 단어 경계에서 시작해 실패하면 같은 덩어리(`[A-Za-z0-9_-]`) 안의 뒤쪽 `eyJ`도 첫 구간 끝이 같아 똑같이 실패하므로 덩어리 끝으로 건너뛴다. 경계가 아닌 자리(`aeyJ`)는 한 글자만 넘긴다(뒤쪽 `-eyJ`는 경계일 수 있음).
  - 재현 명령: 20KB 0.003초, 40KB 0.005초, 80KB 0.011초 (전 0.32/1.39/4.97초). 800KB 0.11초.
  - 명세 정규식과 같은 범위를 내는지 고정 씨앗 입력 3,000개(약 600개 걸림)로 비교하는 테스트를 더했다. 경계가 아닌 자리도 덩어리째 건너뛰는 틀린 구현은 이 테스트가 잡는 것을 확인했다.
- **[중간 2] 개인키 후보 메모리·시간**: `_Candidate`에서 `raw`를 뺐다(범위·가린 값만). 원문은 `_collect`에서 받아들인 걸림에만 `content[start:end]`로 만든다. 또 후보를 전부 모아 정렬하지 않고, 규칙 표 순서대로 규칙마다 흘려 보며 판정한다(각 규칙의 후보는 시작 순서로 나오므로 같은 규칙 안에서는 마지막으로 받은 것과만 겹칠 수 있다). 앞 규칙이 받은 범위는 규칙이 끝날 때 한 번 정렬해 합친다(`insort` 제거).
  - 재현 명령: BEGIN 1만 개(270KB) 최대 메모리 31KB(입력의 0.12배, 전 44MB). BEGIN 여러 개 + END 하나: 54KB 0.04초 → 216KB 0.16초(선형, 전 0.12 → 1.54초), 메모리는 입력의 약 2.3배(원문 = 블록 전체라 한 벌 복사는 필요).
  - "같은 END에 묶이는 중첩 BEGIN은 첫 것만"은 생성 단계에서 거르지 않고 겹침 판정에 맡겼다. 생성 단계에서 거르면, 첫 것이 다른 종류 개인키와 겹쳐 버려졌을 때 뒤쪽 BEGIN이 받아질 수 있는 경우(명세 처리 규칙 2·4)를 잃는다. 결과는 같은 END 묶음에서 하나만 남는다(테스트 `test_F_S01_개인키_BEGIN여러개_END하나`).
- 더한 테스트 5개: `test_F_S01_JWT_eyJ반복_폭주없음`, `test_F_S01_JWT_덩어리_안의_경계에서_시작`, `test_F_S01_JWT_명세_정규식과_같은_범위`, `test_F_S01_개인키_BEGIN반복_메모리`(최대 메모리 < 입력×4), `test_F_S01_개인키_BEGIN여러개_END하나`(2초 안, 메모리 < 입력×4).
- 검증의 다른 지적: 테스트 `test_F_S01_같은_원문은_규칙마다_따로`는 이름이 내용과 달라 `test_F_S01_같은_원문은_키이름이_달라도_하나로_묶는다`로 이름만 바꿨다(기대값 그대로). 낮음 '`_Candidate.raw`의 repr'은 필드가 없어져 사라졌다. 낮음 나머지 3건(`.map` 이름 접두 길이, 사설 영역 표시 문자, `evidence_key` 빈 키)과 보안 중간 3번째(판정 안 된 짧은 값이 근거 조각에 남음)는 명세·설계 판단이라 손대지 않았다.
