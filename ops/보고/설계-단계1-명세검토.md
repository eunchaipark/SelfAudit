## D-016 추천 (취약 라이브러리 목록)

- **받는 방법 (사용자가 정할 것. 외부 서비스·라이선스라서 설계가 정하지 않는다)**
  - A (추천): 사용자가 브라우저로 직접 받아 `<데이터 폴더>/vulndb/jsrepository.json`에 둔다. 앱에는 네트워크 코드가 전혀 없어서 NFR-01이 가장 깨끗하다. 저장소에는 가상 테스트 목록만 둔다.
  - B: 따로 실행하는 갱신 명령(점검 중에는 절대 부르지 않음). 앱에 외부 요청 코드가 하나 생긴다.
  - C: 저장소에 사본을 함께 넣는다. Apache-2.0 고지(NOTICE)가 필요하다. 프로젝트 라이선스가 미결(D-005)이라 지금은 비추천.
- **변환 규칙** (불러올 때 명세 형식으로 바꾼다, F-S04 1 보강)
  - `extractors.filecontent`(+ `filename`은 파일 이름에 적용)만 쓴다. `func`·`ast`·`hashes`·`uri`는 버린다(실행·외부 주소가 필요해서).
  - `§§version§§` → `([0-9][0-9.a-z_\-]+)`로 바꾸고 첫 묶음을 버전으로 본다.
  - `identifiers.CVE[]` + `githubID` → 식별자, `identifiers.summary` → summary.
  - severity: `critical`·`high` → 높음, `medium` → 중간, `low` → 낮음, 그 밖 → 낮음.
  - JS 정규식이 Python에서 컴파일되지 않으면 그 항목만 건너뛰고 개수를 점검 안내에 남긴다.
- **위험 (단계 2에서 잰다)**: 라이브러리 수백 개 × 정규식 약 10개를 20MB에 돌리면 NFR-05(60초)를 넘을 수 있다. 줄이는 방법 후보: 라이브러리 이름 글자로 먼저 거르기. 정규식 시간 제한이 필요해지면 새 라이브러리 승인 요청을 낸다.

## F-S05 추천 (REA)

- **찾기**: 서버가 시작할 때와 점검할 때 `shutil.which("rea")`로 절대 경로를 얻고 `<절대 경로> --version`(5초)을 본다. 셸은 쓰지 않는다.

  - 이 PC의 Node가 v22.19.0인데, REA README의 요구는 22.x ≥ 22.23.4다. REA도 설치돼 있지 않다. 설치와 Node 업그레이드는 사용자 확인이 필요하다.
