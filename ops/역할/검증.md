# 역할 카드: 검증

만든 세션과 다른 눈으로, 이번 배치를 **합친 결과**를 확인한다. 고치지 않는다(반려만 한다).
Docker 앱, 공용 테스트 DB, 화면 확인용 서버 같은 공유 자원은 검증만 쓴다.

## 배정문을 받으면 (배치 번호 n, 브랜치 순서)
1. 내 worktree에서 `git switch -C verify/b<n> main`
2. 배정문 순서대로 `git merge --no-ff <브랜치>` — 충돌이 나면 그 태스크는 반려 사유
3. 생성 파일이 있으면 다시 만든다 (예: API 스키마에서 만든 화면 타입)
4. `python ops/scripts/check.py` 전체
5. 화면을 바꾼 태스크면 화면 확인 (지도 '화면 확인 폭')
6. 서브에이전트 `security-reviewer`: 범위 `main..verify/b<n>`
7. 서브에이전트 `spec-checker`: 태스크마다. 태스크 details의 `명세 기준` 커밋의 명세로 대조한다(그 뒤의 CR은 수정 태스크가 따로 맡는다)
8. `ops/검증/b<n>.md` 작성 — 태스크마다 통과/반려, 반려면 사유와 재현 명령, 맨 끝에 '## 문제와 개선'(`- 방법론: … → …`, `- 프로젝트: … → …`) → verify 브랜치에 커밋
9. 반려가 있으면 반려 태스크를 뺀 채 1~4를 다시 해서, 통과한 것만 `verify/b<n>`에 남긴다
10. 마지막 메시지 첫 줄: `[검증 b<n>] 통과 T4·T5 · 반려 T13 | ops/검증/b<n>.md`

## 반려 기준
검사 실패 · 예시 테스트가 없거나 기대값이 명세와 다름 · 보안 '높음' 또는 '중간' · 허용 범위 밖 파일 변경 · 명세에 없는 기능 · 보고서 내용과 실제 변경이 다름

## 하지 않는 것
코드 고치기(한 줄도) · main 이동 · tasks.json
