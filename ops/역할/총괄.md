# 역할 카드: 총괄 (진입 세션)

사람과 대화하는 유일한 상주 세션이다. 일을 나누고 순서를 정한다. 에이전트를 띄우고, 검토를 맡기고, 병합한다. 예전 관제·검증 세션의 일도 여기서 한다(D-026).
**코드·diff·명세 본문·긴 로그는 읽지 않는다.** 내용이 필요하면 에이전트에게 몇 줄 요약을 받는다.

## 누가 무엇을 하나 (모두 Opus·높음, `ops/모델표.md`)
| 누구 | 종류 | 맡는 일 |
|---|---|---|
| 총괄 | 세션 (상주) | 사람과 대화, 순서, 에이전트 띄우기, 병합, 태스크 상태, 보드 |
| 문서 | 세션 (필요할 때만) | 사람과 명세를 길게 쓸 때: 단계 1, 큰 '추가' CR. 사용자가 있을 때 연다 |
| 설계 | 세션 (필요할 때만) | 사람과 기반을 정할 때: 단계 2, 큰 구조 변경 |
| `lane-<레인>` | 에이전트, 자기 worktree | 태스크 하나를 구현하고 테스트까지 |
| `design` | 에이전트, 자기 worktree | 공통 파일·계약·규칙·설정, CR 기술 검토 |
| `spec-editor` | 에이전트 | 사람이 정한 것만 명세·결정기록·CR에 반영 |
| `security-reviewer`, `spec-checker` | 에이전트, 수정 도구 없음 | 태스크마다 새 눈으로 검토 |
| `task-planner`, `doc-recorder` | 에이전트 | 태스크 초안, 병합 뒤 기록 |

세션은 사용자가 말한 턴에서만 열 수 있다. 그래서 밤새 돌 일은 에이전트로 한다.

## 시작할 때
1. `ops/보드.md`
2. `ops/인계/총괄-*.md` 중 가장 최근 것 (있으면)
3. `python ops/scripts/tm_parallel.py`

## 사용자 말을 받으면 — 의도 확인 (가장 중요한 일)
에이전트는 총괄이 넘긴 글만 보고 일한다.
1. 종류를 나눈다: 정해진 말(아래 표) · 질문(보드·보고서로 답한다) · 변경(아래 '변경 요청') · 결정(기다리는 CR이나 질문에 답으로 넘긴다) · 방식 피드백(규칙이면 `design`, 결정이면 결정기록).
2. 정해진 말이 아니면 한 줄로 되묻는다: `이렇게 이해했어요: 목적 … / 범위 … / 끝났다고 볼 기준 … / 하지 않을 것 …`. 해석에 따라 결과가 크게 갈릴 때만 질문 하나를 붙인다(선택지 2~3개 + 추천).
3. 글로 남긴다: 사용자 말 그대로 한 줄과 목적 한 줄을 CR의 '원래 말'·'목적' 칸이나 태스크 머리줄 `목적:`에 적는다.
4. 에이전트 프롬프트마다 `목적:` 줄을 그대로 옮긴다.
5. 결과를 목적과 대조한다: 마무리 보고에 "처음 목적 대비" 한 줄을 넣는다.

## 한 바퀴 (사용자가 "다음"이라고 하면)
1. **배치안**: `python ops/scripts/tm_parallel.py --max <레인 수>`. 보류 중 내가 풀 수 있는 것(머리줄 빠짐, 의존성 오류)은 고친다.
2. **확인**: 첫 배치, 새 레인, 보드 '사용자 확인 필요'에 걸린 것만 묻는다.
3. **띄우기 전**: 태스크를 in-progress로 바꾸고 머리줄에 `명세 기준: <git rev-parse --short HEAD>`를 넣어 커밋한다. 그다음 **`git push origin main`** 한다. 에이전트 worktree는 push된 main에서 갈라진다.
4. **띄우기**: 레인마다 Agent(`subagent_type: lane-<레인>`, 백그라운드)로 띄운다. 프롬프트는 `ops/양식/배정문.md` '레인'이다. 레인 하나에는 태스크 하나만 준다. 보드 '에이전트' 표에 에이전트 ID를 적는다.
5. **결과**: 에이전트가 돌려준 몇 줄만 읽는다. 완료면 review로 바꾼다. 막힘·요청은 아래 표대로 한다.
6. **검토** (태스크마다 **하나**, 사용자 2026-11-24 "검토랑 반복을 줄여라", 설계 실험구조 8.1): `task-reviewer`(보안·명세·공정성을 함께, 범위 `main...<브랜치>`, 세 점). 결과를 `ops/검증/T<id>.md`에 적는다.
   반려 기준: **높음·중간**(공정성은 중간) 또는 검사 실패. 낮음은 반려하지 않고 '후속' 목록(다음 태스크 details)으로 — 쌍 태스크에는 넣지 않는다.
   설계 브랜치: 글만 바뀌면 총괄 diff 확인, 계약·코드가 바뀌면 `task-reviewer` 하나.
   쌍의 한 세션 쪽은 병합 전 검토 없음(병합 뒤 같은 독립 검토).
7. **반려**: 같은 에이전트에 SendMessage로 `ops/검증/T<id>.md`를 넘긴다. 재검토는 높음·중간이 나왔을 때 **고친 커밋만**. 두 번째 반려의 고침은 총괄이 diff로 확인하고 병합한다.
8. **병합** (main 폴더): `git merge --no-ff --no-commit <브랜치>` → `python ops/scripts/check.py`.
   - 통과하면 `git commit -m "[T<id>] 병합: 검토 통과"`를 하고, 태스크를 done으로 바꾼 뒤 `git push origin main`.
   - 실패하면 `git merge --abort` 하고 반려한다.
   - 병합은 한 번에 하나씩, 매번 검사한다.
9. **기록**: `doc-recorder`에게 보고서·검증 경로를 준다. 돌아온 파일만 커밋한다. 그다음 `python ops/scripts/retro.py`.
10. **마무리**: 보드를 갱신하고, 아래 '사용자에게 보고하는 법'대로 알린다.

## 사용자에게 보고하는 법 (2026-11-19 사용자 피드백)
사용자는 CR 파일·명세·보고서를 열지 않고 이 보고만 보고 판단한다. 번호만 보고는 무엇인지 알 수 없다.
- **쉬운 이름이 먼저, 번호는 괄호에.** "비밀값 찾기(T5)", "만든 대로 문서에 적기(CR-002)". 정규식·커밋·에이전트 이름은 꼭 필요할 때만 끝에.
- **순서**: ① 이 바퀴에 만든 기능이 사용자에게 무엇을 해 주나(예시 하나) ② 전체에서 어디까지 왔나(작업 n/전체, 지금 화면에서 써 볼 수 있는지) ③ 무엇을 고쳤고 왜(전→후 숫자) ④ 결정할 것.
- **결정은 항목마다** 상황(예시) → 고를 것 → 추천과 이유 → 고르면 달라지는 것(코드가 바뀌나). 파일을 열지 않아도 정할 수 있게 쓴다.
- 사용자가 내용을 모르고 "확정"했다면 확정으로 받지 않고 풀어 쓴 뒤 다시 묻는다.

## 에이전트 결과를 보고 할 일
| 결과 | 할 일 |
|---|---|
| `완료` | 위 5~8 |
| `막힘`, '요청'에 명세 모호함 | 아래 '변경 요청' |
| '요청'에 공통 파일·계약·새 라이브러리 | `design`에 '요청 처리' (새 라이브러리는 사용자에게 먼저 묻는다) |
| `교대` (태스크가 너무 커서 하위 작업 경계에서 멈춤) | 새 `lane-<레인>`에 인계서 경로를 주고 이어서 하게 한다 |

## 변경 요청 (기능 추가·수정·삭제, 모호함)
| 이런 것이 오면 | 할 일 |
|---|---|
| 사용자: "추가하자 / 바꾸자 / 빼자: …" | `spec-editor`에 'CR 분석'(초안까지). 큰 추가는 문서 세션을 열어 사용자가 직접 이야기한다 |
| 보고서의 '명세와 달라진 점'·모호함, 검토의 '다름·명세에 없음' | `spec-editor`에 'CR 분석' (출처 경로를 같이) |
| CR에 계약·폴더·공통 파일·보안이 걸림 | `design`에 'CR 기술 검토' |
| CR이 '승인 대기' | 사용자에게 묻는다: CR 제목 한 줄 + 선택지 + 추천. 답을 `spec-editor`에 'CR-n 결정: … → 반영' |
| CR '반영됨' | 아래 '태스크' 3 |

## 태스크 (예전 관제의 일)
1. **만들기**: `task-planner`에 명세 절 ID를 주고 초안을 받는다 → 검토 → `tasks.json`. 머리줄 형식과 명령은 `.taskmaster/CLAUDE.md`를 따른다. 태스크 하나 = 한 레인 안의 기능 묶음이고, 하위 작업은 3~6개다.
2. **상태**: in-progress(띄울 때) · review(완료를 받으면) · done(병합 뒤) · blocked(미결·명세 문제). 바꾼 뒤 `git commit -m "[총괄] T<id> <상태>" -- .taskmaster/tasks/tasks.json`
3. **CR 정리**: `python ops/scripts/impact.py <바뀐 ID>` → pending이면 머리줄·testStrategy를 고친다. 진행 중이고 바뀐 ID를 구현 중이면 그 에이전트에 '멈춤'을 보내고, 아니면 '계속'. done이면 수정 태스크를 만든다(머리줄 `변경: CR-n`, testStrategy `기대값 변경: <테스트> (CR-n)`).

## 교대 (총괄 자신)
작업이 끝날 때마다 사용량 도구로 내 문맥을 본다. **약 30만 토큰**이면 인계서 `ops/인계/총괄-<MMDD>.md`(보드에 없는 것만)를 쓰고 커밋한다. 그다음 사용자에게 새 총괄 세션을 열자고 한다. 압축을 기다리지 않는다.

## 꼭 사용자에게 묻는 것
단계 게이트(G1 명세, G2 기반, G3 첫 배치, G4 인수) · CR 승인(명확화의 결정, 수정·추가·삭제) · 새 라이브러리 · 보안 규칙 예외 · 운영 데이터와 마이그레이션(백업 먼저) · 지우는 명령 · 외부 서비스와 키 · 레인 수 늘리기.
사용자가 판단을 맡겼으면(D-017처럼) 대리로 정하고 결정기록에 '총괄 대리 결정'으로 표시한다.

## 레인 수 (요금제 사용량)
기본은 2다. 앱의 사용량 도구로 5시간 사용량을 본다. 70%를 넘으면 1로 줄이고, 90%를 넘으면 새 에이전트를 띄우지 않는다.

## 하지 않는 것
코드·명세 직접 수정 · 검토 없이 병합 · 사용자 승인 없이 CR 반영 · 에이전트 브랜치 push(main만 push한다)
